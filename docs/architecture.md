# Colonyloom — архитектура мода колоний

**Статус:** рабочая спецификация проектных решений.  
**Редакция:** 0.4 · 2 октября 2026 года.  
**Платформа первого этапа:** Minecraft Java Edition 1.21.1, NeoForge, JDK 21 (64-bit). Другие загрузчики и версии Minecraft — последующие этапы; конкретная матрица поддержки пока не выбрана.  
**Архитектурная основа:** серверный модульный монолит, бюджетируемая симуляция, событийное планирование, отдельное исполнение физических действий в Minecraft.

Документ фиксирует архитектуру, сформированную в обсуждении Colonyloom. Пользовательские требования: идея поселения, подобная MineColonies; качественная архитектура; первый этап на Minecraft 1.21.1 и NeoForge с последующим переносом на другие загрузчики и версии; принудительная загрузка необходимых чанков; несколько сотен жителей суммарно на сервере; возможность дальнейшего развития без переписывания основных механизмов.

Названия модулей, структур и контрактов ниже описывают проектные решения, не замороженный API. Первоначальная редакция создана при наличии только `LICENSE`; теперь в репозитории реализован технический вертикальный срез. Текущий порядок реализации и критерии gates приведены в [плане разработки](development-plan.md), воспроизводимые проверки — в [verification](verification.md), supported matrix и recovery policy — в [operations](operations.md). Документ не обещает конкретный TPS, число жителей на произвольном оборудовании или функциональный паритет с определённым релизом MineColonies.

Из документа-образца Mux заимствованы форма спецификации, явное владение, границы гарантий, статусы решений и критерии проверки. Плагинный runtime, отдельные процессы, protobuf и другие технологии Mux в Colonyloom автоматически не переносятся. [Д0, Д1]

В редакции 0.2 по результатам архитектурного аудита уточнены обязательства снабжения, предотвращение ресурсных блокировок, лимиты активного состояния, идентичность воплощения жителя, восстановление исторических фактов и права отложенных операций. Ранние измерения платформы и выбор восстановительной политики перенесены перед сквозной экономикой. Это уточнение спецификации, не отчёт о проверенной реализации.

В редакции 0.3 разделены историческая доставка, текущее выделение и расход материалов; закреплены продвижение графа при полном лимите, резерв состояния критических цепочек, пространственный арбитраж целей и каноническая идентичность запасов. Уточнены порционное комплектование, безопасная смена активных областей, часы неактивных жителей и пробуждения при заполненной очереди. Сквозной пример, восстановление и критерии проверки приведены к этим контрактам. Это исправления спецификации по повторному аудиту, не результаты испытаний мода.

В редакции 0.4 по выбору пользователя зафиксирована первая целевая пара: Minecraft 1.21.1 + NeoForge. JDK 21 (64-bit) соответствует требованиям этой платформы [Н1]. Перенос на другие загрузчики и версии остаётся направлением развития, а не условием завершения первого этапа; границы общей логики и адаптеров сохраняются.

## 1. Назначение и границы

Colonyloom — симуляция развивающейся колонии в физическом мире Minecraft. Игрок управляет населением, территорией, строительством, экономикой, исследованиями и обороной. Жители выполняют работы, потребляют ресурсы, перемещаются и взаимодействуют с реальными блоками и инвентарями.

Основной игровой цикл:

```text
Население → потребности → добыча → производство → доставка
    ↑                                               ↓
    └──────────── развитие ← строительство ──────────┘

Питание, сон, болезни, смерти и нападения меняют доступность работников.
```

### 1.1. Основная граница

**Ядро обеспечивает жизненный цикл работ, владение состоянием, планирование и ограничения исполнения. Игровые системы определяют цели, правила и специальные способы выполнения.**

Профессия не реализует заново поиск запасов, доставку, загрузку чанков, сохранение и общий механизм ожидания. Но специальное поведение шахтёра, врача или бойца не обязано выражаться одним универсальным сценарием.

Общая сложность решается один раз; предметные различия не скрываются за чрезмерно универсальной абстракцией.

### 1.2. Не входит автоматически

- Отдельный сервер симуляции, микросервисы или распределённые колонии.
- Полноценный автономный движок, заменяющий Minecraft.
- ECS для всех объектов только ради архитектурного стиля.
- Глобальный event sourcing, брокер сообщений или база данных вместо обычного хранения мира.
- Универсальный визуальный редактор AI и произвольный скриптовый runtime.
- Одновременная поддержка нескольких версий Minecraft в первом этапе. Последующий перенос выбран как направление развития; список версий и сроки их сопровождения определяются отдельно.
- Фоновое производство при выключенном сервере.
- Полноценная дипломатическая экономика и автоматическая межколониальная торговля.

Возможность расширить архитектуру не означает, что эти функции уже выбраны для реализации.

## 3. Логическое устройство и потоки

Симуляция находится в процессе Minecraft-сервера. В одиночной игре используется та же серверная модель внутри integrated server; клиент не становится владельцем экономики.

```text
Клиент
  ├─ интерфейс, визуализация, предпросмотр
  └─ команды игрока / подписки на представления
                   │
                   ▼
Адаптер загрузчика + общая Minecraft-интеграция
                   │
                   ▼
ServerRuntime
  ├─ ColonyRegistry
  ├─ SimulationScheduler + GlobalWorkBudgets
  ├─ ChunkDemandManager
  ├─ арбитраж областей физических целей
  ├─ арбитраж пересекающихся физических запасов
  └─ ColonyRuntime × N
       ├─ жители, здания, территория
       ├─ WorkBoard и назначения
       ├─ SupplyPlanner и Reservations
       ├─ производные индексы
       └─ расписание обновлений
                   │
                   ▼
Исполнители Minecraft
  └─ сущности, навигация, блоки, инвентари, бой
```

### 3.1. Правило записи

Авторитетное изменяемое состояние принадлежит серверному потоку. Сетевой обработчик, callback загрузчика и фоновая задача не получают права изменять его с произвольного потока.

Фоновое вычисление получает ограниченный снимок и возвращает результат с идентификатором запроса и ревизиями исходных данных. Сервер проверяет актуальность перед применением. Устаревший результат отбрасывается или становится основанием для нового расчёта.

Фоновой поток не читает произвольно живой `Level`, сущности, чанки и инвентари. Стоимость подготовки снимка и его памяти также учитывается; асинхронность не делает копирование бесплатным.

### 3.2. Области состояния

Каждая колония — независимая область данных и планирования. Обычный поиск работы или ресурсов не обходит другие колонии. Межколониальные операции, если будут добавлены, используют явные обязательства и перевозки, а не общий изменяемый склад.

Исключение из локальности — серверный арбитраж действительно общих физических ресурсов: пересекающихся областей целей (§12.4) и представлений одного запаса (§9.1). Он предотвращает конфликт обещаний и изменений, но не открывает колониям поиск, права доступа или неявную торговлю ресурсами друг друга.

Изоляция колоний логическая, не процессная: авария JVM или исчерпание памяти затрагивает весь сервер.

## 4. Модули и направление зависимостей

### 4.1. Физические модули сборки

| Модуль | Ответственность | Разрешённые зависимости |
|---|---|---|
| `colonyloom-core` | Модель состояния, идентичность, работы, планировщик, снабжение и базовые контракты | Стандартная библиотека и обоснованные независимые библиотеки; без Minecraft и загрузчиков |
| `colonyloom-gameplay` | Строительство, профессии, потребности, исследования, оборона, квесты | `core` |
| `colonyloom-minecraft` | Мир, сущности, навигация, инвентари, хранение, сеть, общая клиентская часть | `core`, `gameplay`, выбранная версия Minecraft |
| `colonyloom-<loader>` | Регистрация, события, платформенный транспорт, билеты чанков и отличающиеся API | `minecraft` и API конкретного загрузчика |

```text
loader-a ─┐
          ├─→ minecraft ─→ gameplay ─→ core
loader-b ─┘        └──────────────────→ core
```

Нижние модули не импортируют верхние. Контракт внешней операции находится на стороне потребителя, реализация — в интеграции. Composition root собирает конкретные реализации при запуске.

Это выбранные границы сборки, но не требование отдельного Gradle-модуля на каждую профессию. Внутри модулей используются пакеты по ответственности. Не создаётся отдельный SDK-модуль до появления достаточного стабильного контракта расширений.

В первом этапе реализуется только `colonyloom-neoforge` для Minecraft 1.21.1; `loader-a`/`loader-b` на схеме обозначают возможность расширения, не два обязательных стартовых модуля. Пустые адаптеры будущих загрузчиков не создаются. `core` и `gameplay` сохраняют независимость от платформы; `minecraft` пока рассчитан на одну версию игры. Версионные адаптации выделяются по реальным различиям при первом переносе, без преждевременной копии всего API Minecraft.

## 5. Владение данными и идентичность

### 5.1. Источники истины

| Данные | Авторитетный владелец | Производное представление |
|---|---|---|
| Колония, принадлежность и права | Запись колонии | Карта и клиентская сводка |
| Личность, навыки, дом, профессия | Запись жителя | UI жителя, данные отображения сущности |
| Физическое положение и движение | Сущность Minecraft | Последнее известное положение, пространственный индекс |
| Цель, этап и исполнитель | Работа | Очередь интерфейса |
| Потребности, резервы, выделения и обязательства снабжения | Снабжение; общие физические запасы проходят серверный арбитраж | Агрегированная сводка дефицита и обеспечения |
| Реальные предметы | Инвентари Minecraft | Индекс запасов |
| Реальные блоки | Мир Minecraft | Прогресс стройки и кеш проходимости |
| Рецепты, профессии и чертежи | Определения контента | Индексы производителей и доступности |

Индекс запасов не создаёт предметы. Сохранённый прогресс стройки не доказывает наличие блока. Клиентское сообщение не доказывает наличие права или ресурса.

### 5.2. Житель и сущность

```text
CitizenRecord                         CitizenEntity
  citizenId                             citizenId
  bindingEpoch / entityId                bindingEpoch / entity UUID
  colonyId                              движение и анимация
  homeId / workplaceId                  физическое исполнение
  skills / needs                        состояние сущности Minecraft
  assignedWorkId
  lifecycleState
```

Запись жителя долговечна. Связь с сущностью восстанавливается по стабильному ID. Отсутствие сущности, её смерть, выгрузка чанка и удаление жителя — разные события.

Стабильный `citizenId` обозначает личность, а сохраняемые `bindingEpoch` и `entityId` — разрешённое физическое воплощение. Серверный реестр допускает не более одной активной привязки к записи. Новое воплощение создаётся только явным переходом lifecycle с новой эпохой; отсутствие загруженной сущности не разрешает создавать замену. Runtime-generation и поколение компактного handle не заменяют эпоху воплощения.

Сущность привязывается только после чтения записи и сверки ID, эпохи и разрешённого entity UUID. При удалении жителя сохраняется маркер удаления, достаточный для отклонения поздно загруженного старого воплощения; его удаление требует отдельной безопасной политики очистки. Сущности без записи, устаревшие воплощения и конфликтующие дубликаты не исполняют работы и не предоставляют инвентарь снабжению до разрешения конфликта. Их данные и имущество не удаляются автоматически и не выдаются повторно; применяется предметная политика восстановления (§17.4) с диагностикой.

Поля не дублируются как два независимых источника истины. Например, текущее здоровье привязанной сущности не должно независимо уменьшаться в двух системах; конкретный мост здоровья определяется при интеграции с выбранной версией Minecraft.

### 5.3. Идентификаторы и горячие структуры

- Долговременные ссылки используют стабильные IDs; контент — namespaced IDs.
- Позиция внешнего объекта включает измерение, а не только координаты.
- Внутренний компактный индекс допустим для горячего доступа, но не сохраняется как долговременная идентичность.
- Если слот переиспользуется, runtime-handle содержит поколение, чтобы старая ссылка не указывала на нового жителя или работу.
- Долгоживущие работы не удерживают `Entity`, `Level`, объект инвентаря или загруженный чанк напрямую.

### 5.4. Владение временными ресурсами

| Ресурс | Владелец | Завершение владельца |
|---|---|---|
| Назначение и ожидания работы | Работа | Назначение снимается, ожидания отключаются |
| Резерв | Потребность/работа | Неиспользованный резерв освобождается |
| Выделение у потребителя | Потребность/работа до расхода, утраты или освобождения | Остаток возвращается в свободный запас либо получает явное назначение; историческая доставка не откатывается |
| Область физической цели | Цель; исключительность проверяет серверный арбитр | После прекращения физических действий область освобождается |
| Предметы в пути | Реальный инвентарь перевозчика или другое явное хранилище | Не исчезают из-за снятия резерва; требуют обработки результата |
| Запрос маршрута | Исполнитель и версия цели | Результат становится недействительным |
| Требование чанка | Колония, здание или активная операция | Требование снимается; другие владельцы продолжают удержание |
| Подписка UI | Соединение, открытое представление и актуальное право чтения | Снимается при закрытии, отключении или утрате доступа |

Отмена работы не равна откату уже изменённого мира или телепортации груза на склад.

## 6. Планировщик и бюджеты нагрузки

### 6.1. Принцип обновлений

Нет общего цикла «каждый житель анализирует всё каждый тик». Система регистрирует ближайшее необходимое обновление или пробуждается по изменению условия.

| Причина | Действие |
|---|---|
| Появилась работа / освободился исполнитель | Ограниченный проход назначения |
| Прибыли материалы | Пробуждение связанных потребностей и работ |
| Достигнут порог голода | Планирование получения еды |
| Сменилось расписание | Изменение намерения; физический переход планируется отдельно |
| Изменился рабочий участок | Инвалидация затронутых проверок и маршрутов |
| Наступил срок действия | Выполнение запланированного шага |

Начальная структура — очередь ближайших обновлений по категориям и очереди готовых работ. Собственный сложный таймерный движок не является обязательным условием.

### 6.2. Глобальные ограничения

Бюджеты принадлежат серверу, а не умножаются на количество колоний. Отдельно ограничиваются:

- назначение работников;
- планирование цепочек снабжения;
- запуски поиска пути и объём управляемого поиска;
- сравнение участков чертежей;
- физические строительные действия;
- сверка хранилищ;
- новые запросы загрузки чанков;
- подготовка сетевых представлений.

Используются измеримые единицы работы и временной предохранитель. Дорогой алгоритм должен уступать управление между порциями. Проверка времени после завершения монолитного вызова не защищает от уже случившегося длинного тика.

Для внешнего неприостанавливаемого вызова можно ограничить число запусков, но нельзя обещать жёсткий предел его времени. Такие вызовы измеряются отдельно; при неприемлемой стоимости нужен другой способ исполнения.

Бюджет этих очередей не ограничивает автоматически стоимость тиков сущностей, движения, столкновений, боя и каскадов обновления блоков. Они измеряются отдельно вместе с базовой нагрузкой удерживаемых чанков. Ограничение числа физических действий не является гарантией ограниченной стоимости всех вызванных ими изменений мира.

### 6.3. Справедливость и перегрузка

Колонии обслуживаются по очереди с приоритетами и учётом возраста ожидающей работы. Крупная колония не получает весь бюджет только потому, что у неё больше задач.

Ожидающая работа паркуется на конкретной причине, а не заново опрашивается каждый тик. Повторяющиеся уведомления объединяются. Очереди временных вычислений имеют пределы; при перегрузке новые вычисления откладываются, а уже принятая игровая потребность остаётся зарегистрированной в пределах лимитов долговременного состояния (§6.5).

Объединение уведомлений не теряет необходимость обработки: у допущенного объекта сохраняется runtime-признак `dirty/pending` и ревизия последнего обработанного изменения. Если очередь заполнена, признак остаётся установленным; продолжаемый курсор с гарантированной долей обслуживания повторно ставит такие объекты в очередь без полного опроса каждый тик. После обработки признак снимается только для обработанной ревизии; более новое изменение требует следующего прохода. Число признаков и регистраций ожидания ограничено допущенным состоянием. После загрузки ожидания восстанавливаются из сохраняемых причин и заново проверяются, а не зависят от сохранности оперативной очереди.

Невыполненный физический перенос или пользовательская команда не отбрасываются молча ради короткой очереди. Отклонение команды содержит явную причину.

### 6.4. Одновременные события

Рассвет, тревога и массовое завершение условий не запускают сотни дорогих действий в одном тике. Общее состояние меняется сразу; поиск путей, назначения и вторичные пересчёты распределяются по тикам.

Низкочастотная симуляция не подменяет физику: нельзя «догнать» пропущенные тики строительством без проверки мира. Диспетчер использует монотонное серверное время; игровые сутки Minecraft задают фазу расписания, а собственные потребности жителя — его активное время (§13). Выключенный сервер по умолчанию не производит ресурсы.

### 6.5. Пределы накопленного состояния

Объём работы за тик и объём накопленного состояния ограничиваются независимо. До допуска нагрузки задаются серверные пределы принятых работ, потребностей, обязательств, узлов и рёбер раскрытого графа, а также доли колоний. Отдельно ограничиваются живые сущности, исторические свидетельства, кеши и удерживаемые чанки. Числа определяются измерениями; отсутствие выбранного числа не означает неограниченность структуры.

Одинаковые совместимые потребности объединяются с сохранением количества и владельцев. Граф раскрывается лениво до общего предела, затем сохраняется компактная причина ожидания без дальнейшего роста фронта. Достижение вычислительного лимита не объявляет рецепт неразрешимым. Новая команда, превышающая лимит состояния, отклоняется до создания обязательств; автономная цель хранит ограниченное агрегированное ожидание вместо генерации новых заказов каждый тик.

Предел графа не должен создавать тупик из одних незавершённых фронтов. Исходная политика — порционно продвигать выбранную ветвь к исполнимому листу, а при нехватке места сворачивать незапущенные спекулятивные ветви других целей в компактные ожидания. Сворачивание сохраняет цель и принадлежность долей, не удаляет реальные грузы, начатые процессы, подтверждённые результаты и восстановительные свидетельства. Для разрешимой цепи, чьё рабочее множество вместе с обязательным состоянием помещается в допуск, должна освобождаться ёмкость для продвижения; выбор учитывает приоритет и возраст. Если минимальное рабочее множество не помещается, показывается отдельная блокировка ёмкости, а не отсутствие рецепта. Компактные ожидания также входят в лимит; возможность ручной отмены не заменяет эту гарантию прогресса.

Освобождение ресурсов, отмена и восстановление уже принятых операций должны оставаться возможны при исчерпании лимита: необходимая служебная ёмкость учитывается при допуске работы. Завершённые объекты очищаются только после закрытия зависимостей и сохранения необходимых свидетельств; реальные грузы не удаляются ради освобождения записи.

### 6.6. Жизненно важные работы

Питание, реакция на угрозу и освобождение заблокированной логистики имеют выделяемую долю обслуживания и измеряемую допустимую задержку. Срочность потребителя передаётся необходимым производственным, транспортным и навигационным зависимостям; после снятия причины она пересчитывается. Возраст работы предотвращает голодание обычных категорий, но не подменяет сроки критических действий.

Доля CPU дополняется резервом ёмкости состояния для новых критических потребностей и их минимальных производственных, транспортных и навигационных зависимостей. При допуске населения и обычных работ этот резерв учитывается отдельно от служебной ёмкости отмены/восстановления; некритическая работа не может занять его ни напрямую, ни через раскрытие графа. Размеры и число одновременно поддерживаемых критических цепочек входят в профиль нагрузки. Дополнительно допускается безопасное сворачивание незапущенных некритических фронтов (§6.5), но не удаление уже начатых эффектов. Нехватка критического резерва показывается как отдельная причина перегрузки; новый критический заказ не обязан ждать завершения всех ранее принятых строек только из-за занятой ими памяти.

В пределах принятого профиля нагрузки проверяется продвижение критических цепочек, а не только исполнение верхнеуровневой задачи. При превышении доступной мощности ограничивается допуск некритической работы и показывается нарушение срока. Нельзя обещать дедлайн при отсутствии ресурса, запрещённом действии или неготовом чанке; эти причины отделены от задержки планировщика.

## 7. Работы, назначения и действия

### 7.1. Работа

Проектная модель:

```text
WorkOrder
  id / typeId / owner
  target / priority
  state / assignee
  progress / dependencies
  waitingReason / revision
```

Общий жизненный цикл:

```text
Planned → Ready → Assigned → Running → Completed
             ↑        │         │
             └──── Waiting ─────┘

Допустимое незавершённое состояние → Cancelled / Failed
```

Причины ожидания типизированы: материалы, инструмент, исполнитель, вместимость, доступность участка, готовность чанка, сверка после загрузки, предел активного состояния и ограничение бюджета. Временное препятствие не считается окончательной ошибкой.

Проверка условия и регистрация ожидания выполняются без уступки управления либо регистрация завершается повторной проверкой ревизии и условия. При изменении между порциями работа помечается готовой к повторной проверке, а не остаётся спящей до следующего случайного события. При пробуждении условия проверяются заново: наличие уведомления не гарантирует, что условие всё ещё выполнено. Повторная постановка при заполненной очереди следует контракту §6.3.

### 7.2. Назначение

Работы индексируются по специализации, области и готовности. Из подходящих свободных жителей выбирается ограниченное число кандидатов. Оценка учитывает навыки, примерное расстояние, оснащение и текущие обязательства.

Полный поиск пути не запускается для каждой пары «житель — работа». Дорогая проверка применяется к отобранному кандидату; недоступная цель исключается до релевантного изменения или следующей отложенной попытки.

У жителя одно активное физическое исполнение. Тревога, голод или сон могут его прервать по правилам профессии. При этом производственная цель может сохраняться, а действия и ресурсы освобождаются по явной политике.

При парковке отдельно решается судьба назначения, груза и резервов. Работа не удерживает единственного исполнителя или вместимость, необходимые для устранения причины её ожидания: сначала выполняется безопасное освобождение по предметной политике (§8.3, §9.2), затем назначение снимается. Снятие назначения само по себе не освобождает занятый грузом инвентарь.

### 7.3. Действия

Общие операции: движение, получение/передача предметов, взаимодействие, размещение/разрушение блока, обработка рецепта, ожидание, атака.

Результат исполнения различает:

| Результат | Смысл |
|---|---|
| Progress | Подтверждён частичный результат; можно планировать следующий шаг |
| Completed | Условия завершения действия проверены |
| Waiting | Известно, какое условие мешает продолжить |
| Invalidated | План устарел; требуется ограниченное перепланирование |
| Failed | Продолжение невозможно по предметной причине |

Это семантика, не закреплённые сигнатуры Java API. В горячем цикле не требуется создавать новый объект результата, если достаточно компактного статуса и принадлежащего работе состояния.

### 7.4. Специализация

Работа задаёт цель; исполнитель знает, как выполнить её в мире. Реальная шахта, симулируемая экспедиция, лечение и бой используют общий lifecycle, но не обязаны иметь одинаковый внутренний автомат.

Не вводится универсальный язык workflow с сериализацией callback. Сохраняется явный этап и данные предметного процесса.

## 8. Снабжение и граф потребностей

### 8.1. Разделение сущностей

| Сущность | Значение |
|---|---|
| `Demand` | Кому, что и сколько требуется |
| `ProductionOrder` | Что изготовить и по какому процессу |
| `Reservation` | Какие доступные ресурсы обещаны потребителю |
| `DeliveryOrder` | Какой груз переместить между источником и получателем |
| Обязательство покрытия | Какая часть конкретного `Demand` уже обеспечивается резервом, производством или грузом; не дополнительный запас предметов |
| Выделение у потребителя | Уже доставленный реальный запас, закреплённый за целью до расхода; не свободный запас и не исторический счётчик доставки |

Одна работа может породить несколько потребностей и доставок. Несколько совместимых потребностей могут обслуживаться общей производственной партией, но принадлежность результата и количество для каждого потребителя сохраняются.

Мастерская нового заказа выбирается среди назначенных живым производителям нужной профессии в той же колонии и измерении: минимальное Manhattan-расстояние от оборудования до получателя, при равенстве — стабильный UUID. Объединение совместимых потребностей ограничено выбранной мастерской; независимые локальные мастерские не сводятся к первому зарегистрированному производителю. Уже закреплённая мастерская и начатая партия не переназначаются.

Общая партия принадлежит `ProductionOrder`, а не первой создавшей её стройке. Связи с потребителями содержат количество и собственный lifecycle. Отмена одного потребителя снимает только его долю; ещё не начатый объём пересчитывается с учётом размера партии, освобождаются лишь более не нужные ингредиенты и резервы. Общий заказ отменяется при отсутствии оставшихся обязательств. Для уже начатой неделимой партии неизбежный излишек получает явное назначение в допустимое хранилище; другие потребители не теряют свою долю.

### 8.2. Разрешение потребности

```text
Потребность → вычесть исполненную часть, выделение у потребителя и активное покрытие
  → локальный доступный запас
  → доступный складской запас
  → подходящий производитель и рецепт
  → потребности в ингредиентах
  → ожидание игрока или внешнего источника, если цепочка неразрешима
```

Граф раскрывается порциями. Обязательны обнаружение циклов рецептов, ограничение объёма одного прохода и сохранение причины невозможности. Изменение одного ингредиента не пересобирает все планы колонии.

Ограничение одного прохода не заменяет общий предел узлов, рёбер и активных заказов (§6.5). Цикл одной ветви не делает всю потребность неразрешимой: учитываются исходный запас и допустимые альтернативы. Поиск альтернатив также порционный; исчерпание бюджета или предела раскрытия означает ожидание расчёта, а не доказательство отсутствия решения.

Выбор рецепта учитывает ограничения профессии и здания. Наличие рецепта в Minecraft не означает, что любой житель способен его выполнить.

Для потребности различаются требуемое количество, исполненная часть цели, текущее выделение у потребителя и ещё не исполненное покрытие. Новый заказ создаётся только на `max(0, требуемое − исполненное − выделенное − активное покрытие)`. Для производственной или строительной цели исполнение подтверждается расходом на соответствующий результат по предметной политике; передача материала в инвентарь ещё не является исполнением. Для самостоятельной цели доставки подтверждённая передача является исполнением, и выделение у получателя для этой цели не сохраняется. Семантика цели фиксируется при её создании. Исторический счётчик доставленного количества для квестов отделён от этих величин. При уменьшении цели лишние выделения и покрытие освобождаются по стадии исполнения; уже изъятый груз и неизбежный выход партии обрабатываются явно, а не исчезают из-за изменения счётчика.

Одна доля обеспечения в каждый момент представлена ровно одной стадией: резерв готового предмета, обещанный выход производства, выделенный груз в пути, выделение у потребителя либо исполненная часть цели. Первые три стадии образуют активное покрытие; производство и доставка одной доли не суммируются. Переход стадии и изменение обязательства выполняются вместе на серверном потоке. Подтверждённая передача уменьшает покрытие и увеличивает выделение у потребителя либо исполненную часть цели доставки; расход переводит выделение в исполненную часть. Резервы ингредиентов относятся к их собственным потребностям, а не к дополнительному покрытию конечного изделия.

Выделение у потребителя связано с реальным запасом и исключено из свободного количества для других работ. Его lifecycle продолжается после завершения доставки до расхода, освобождения или подтверждённой утраты. Изменения инвентаря обнаруживаются уведомлениями и сверкой (§10), наличие перепроверяется перед расходом. Доказанная утрата неиспользованного выделения уменьшает только эту долю и снова открывает дефицит; исторический факт доставки не откатывается. При переносе имущества после смерти связь восстанавливается с фактическим местом хранения либо доля признаётся утраченной по предметной политике. Неизвестность после загрузки не снимает выделение и не разрешает повторный заказ (§17.2). Возврат остатка в свободный запас при отмене или новом комплектовании также закрывает соответствующее выделение, а не оставляет фиктивное обеспечение.

### 8.3. Резервы

Резерв содержит потребителя, канонический источник и область физического запаса (§9.1), описание предмета и количество. Он предотвращает обещание одного доступного объёма нескольким работам, но не блокирует внешнего игрока или другой мод от изменения инвентаря.

Проверки: при создании резерва, при извлечении и при передаче. При пропаже запасов резерв становится необеспеченным, и план пересматривается. Отсутствие предмета не компенсируется созданием предмета из счётчика.

Частичная поставка переводит ровно подтверждённое количество в выделение у потребителя либо исполнение самостоятельной цели доставки (§8.2). Снятие резерва не означает, что уже изъятый груз вернулся в источник.

**Арбитраж комплектования:** исходная политика — обещать готовые ингредиенты полным комплектом одной ограниченной исполнимой партии за один серверный шаг, без уступки между финальной проверкой и записью резервов. Поиск источников и точный подбор предметов выполняются порционно до этого шага. Атомарный шаг получает заранее ограниченный набор позиций, заново проверяет их актуальность и либо резервирует весь комплект, либо не создаёт новых частичных резервов. При устаревании кандидатов выполняется ограниченное перепланирование, а не расширение поиска внутри шага. Недостающее производство планируется через обязательства покрытия. Контракт процесса ограничивает размер партии, число ингредиентов, проверяемых источников/слотов и внешних обращений; размер выхода сам по себе не ограничивает стоимость поиска. Неприостанавливаемые внешние вызовы сохраняют оговорки §6.2.

При внешней утрате части комплекта неиспользованные резервы этого комплекта освобождаются, а полученные, но ещё не потреблённые предметы безопасно размещаются перед новым комплектованием. Приоритет, возраст и стабильный порядок разрешают конкуренцию; алгоритм не должен повторно делить X и Y между двумя заказами, каждый из которых требует оба предмета. Исполнитель не удерживается во время ожидания комплектования. Это атомарность логических обещаний на одном потоке, не гарантия неизменности сторонних инвентарей.

## 9. Логистика, хранилища и предметы

### 9.1. Хранилища

Minecraft остаётся владельцем физических предметов. Общий контракт доступа к хранилищу предоставляет поиск, проверку возможности операции и выполнение с фактическим результатом. Конкретные API загрузчиков скрыты интеграцией.

Предварительная проверка не является транзакционной гарантией. Сторонний инвентарь может изменить условия; операция обрабатывает фактически принятый или извлечённый объём.

`StorageAccess` различает адрес доступа (сторона, обёртка, составное представление) и каноническую идентичность резервируемого физического запаса. Адаптер предоставляет идентичность и область пересечения так, чтобы представления одних предметов разделяли один учёт резервов и выделений у потребителей, в том числе при регистрации в разных колониях. Общим является только арбитраж пересекающегося запаса, не поиск ресурсов между колониями. Слоты или диапазоны используются, если это соответствует реальной модели хранилища; для агрегированного хранилища нужна эквивалентная гарантия его API. Повторная регистрация представления не добавляет запас. Замена контейнера по тому же адресу или изменение состава представления инвалидирует прежнюю привязку и требует сверки; одного совпадения координат недостаточно.

Если адаптер не может установить тождество и пересечения, такое представление явно не поддерживается для автоматического резервирования и снабжения. Оно не считается независимым источником по умолчанию. Идентичность запаса не предоставляет права доступа: конкретный путь чтения/изъятия по-прежнему проверяется по §15.1.

### 9.2. Доставка

```text
Запланирована → источник готов → груз получен
              → перенос → груз передан → завершена
```

Груз хранится в реальном инвентаре. Заполненный получатель переводит доставку в ожидание вместимости, отличное от дефицита материалов. До получения груза проверяются вместимость назначения и предусмотренный путь безопасного возврата либо промежуточного размещения; проверка не гарантирует, что сторонний инвентарь не изменится во время пути.

При невозможности передачи исполнитель сначала пытается разместить груз по этому пути, затем освобождает назначение и грузовую вместимость для других работ, включая вывоз продукции из заполненной мастерской. Простое снятие назначения при полном инвентаре не считается освобождением. Промежуточное размещение не завершает исходный `Demand`: покрытие остаётся связано с реальным грузом либо явно снимается при передаче в свободный запас.

Если безопасное размещение стало невозможно, груз сохраняется, показывается отдельная блокировка вместимости и прекращается допуск доставок, усугубляющих её; требуется освобождение места другим исполнителем или игроком. Телепортация, удаление груза и бесконечное скрытое ожидание единственного курьера не являются способом восстановления прогресса. При смерти перевозчика предметы учитываются по механике смерти и сверки обязательств, а не остаются доступными только в логической записи доставки.

Отмена до получения груза освобождает резерв. Отмена после получения создаёт необходимость безопасно разместить реальный груз; исходная потребность и возврат груза не смешиваются в одно фиктивное завершение.

### 9.3. Идентичность предмета

Для точного соответствия недостаточно registry ID. Учитываются значимые компоненты: тип зелья, свойства инструмента, материалы декоративного блока и другие данные выбранной версии Minecraft.

Грубый индекс сокращает кандидатов, затем применяется точная проверка. Идентификатор интернированного описания действует в пределах runtime; в сохранении хранится устойчивое описание. Изменяемый `ItemStack` не становится ключом кеша без контроля изменений.

## 10. Индексы и работа с памятью

Нужны конкретные производные индексы, а не универсальная база запросов:

- здания и участки по чанкам;
- свободные жители по специализации;
- работы по состоянию и требованиям;
- свободное жильё и рабочие места;
- источники предметов и производители;
- потребители, ожидающие определённый ресурс;
- активные стройки и затронутые маршруты.

Свои операции обновляют индекс сразу. Для изменений игроков и других модов используются доступные уведомления и ограниченная периодическая сверка. Перед физическим действием данные перепроверяются.

Для сверяемых хранилищ учитывается возраст последнего наблюдения. Обход имеет продолжаемый курсор и долю бюджета, обеспечивающую обслуживание всех допущенных хранилищ, а не только часто изменяющихся. Допустимый возраст индекса и задержка обнаружения поступившего ресурса входят в профиль нагрузки. При превышении срока источник отмечается устаревшим; отсутствие уведомления не доказывает отсутствие предмета. Отдельно измеряются число просмотренных слотов, стоимость сторонних API и задержка пробуждения потребностей.

Кеши имеют явный предел записей или учитываемой памяти и политику вытеснения. Конечный lifecycle владельца определяет очистку, но не заменяет предел пикового размера; суммарный размер кешей владельцев также ограничивается. Производные индексы ограничены числом допущенных объектов и связей (§6.5). Недоступная цель не навсегда остаётся отрицательным результатом после изменения мира.

В горячих циклах избегаем временных коллекций, stream-конвейеров с выделениями, повторного построения строк, копирования `ItemStack` и создания объекта на каждый блок. Большие общие данные чертежей и определений неизменяемы и разделяются экземплярами.

Уплотнение структур применяется по измерениям. Object pooling всех объектов, собственный allocator и тотальный перевод модели в массивы не выбраны как обязательная основа.

## 11. Навигация

### 11.1. Общий сервис

`NavigationService` управляет запросами, приоритетами, отменой, задержкой повторного поиска и применением результатов. Конкретный поиск пути подключается за этой границей.

Сначала используется подходящий механизм выбранной версии Minecraft. Если его монолитная стоимость не укладывается в требования, необходим управляемый порционный или безопасно асинхронный поиск, а не только очередь вокруг слишком дорогого вызова.

### 11.2. Два масштаба как проверяемая оптимизация

Начальный вариант использует выбранный локальный backend. Иерархия вводится только если сравнение на воспроизводимой нагрузке показывает выигрыш с учётом построения, обновления и памяти общего графа:

- Общий граф проходов: входы, дороги, мосты, переходы и рабочие участки.
- Локальный маршрут по блокам для физического движения к очередной цели.

При выборе иерархии общий граф переиспользует знание о территории, но не объявляет один точный путь пригодным для любого типа жителя. Габариты, способы движения и особые требования исполнителя участвуют в проверке. Сам граф имеет предел активной области и бюджета обновления; проверяются частые изменения дорог, неуспешные запросы и стоимость подготовки снимков. Управляемая граница навигации обязательна, двухуровневый backend — нет.

### 11.3. Актуальность

Запрос связан с жителем, версией цели и ревизиями затронутых участков. Отмена или новая цель делает старый результат недействительным. Изменение участка затрагивает соответствующие маршруты, а не всю колонию.

Полнота уведомлений внешних изменений не гарантируется: исполнитель также обнаруживает физическое препятствие. Повторный поиск имеет задержку и причину, иначе недостижимая цель создаст постоянный поток запросов.

Состояние маршрута — производное. Сохранение мира не обязано сохранять внутреннюю очередь поискового алгоритма.

## 12. Строительство и чертежи

### 12.1. Разделение определения и экземпляра

```text
Blueprint                           ConstructionSite
  palette                             blueprintId / version
  compact block data                  transform / targetLevel
  functional markers                  progress / activeSections
  metadata                            workIds / revision
```

Один чертёж используется несколькими стройками. У экземпляра собственные положение, поворот, прогресс и связанные работы. Копия полного чертежа каждому строителю не нужна.

### 12.2. Порционное исполнение

1. Выбрать ограниченный участок.
2. Сравнить ожидаемое и фактическое состояние.
3. Определить допустимый порядок действий.
4. Запросить ближайшую порцию материалов.
5. Выполнить доступные действия в пределах бюджета.
6. Сохранить подтверждённый прогресс.

Не создаём отдельную высокоуровневую работу на каждый блок большого здания. Работы представляют участки или этапы; операции над блоками выполняются внутри исполнителя.

### 12.3. Физические проверки

Перед действием проверяются блок, допустимость замены, актуальное пространственное владение цели (§12.4), готовность чанка, актуальные права субъекта операции (§15.1), наличие материалов и ограничения интеграции. Обработчики событий Minecraft и сторонних модов могут отклонить изменение; завершение не объявляется только по намерению поставить блок.

Игрок может изменить готовый участок. Прогресс ускоряет продолжение, но не заменяет сверку с миром. Стройка не должна по умолчанию уничтожать произвольные контейнеры и их содержимое: правила замены опасных блоков требуют явной политики.

Обновление чертежа во время стройки не подменяет незаметно её цель. Конкретный механизм фиксации версии/снимка чертежа определяется вместе с форматом контента (§24).

### 12.4. Арбитраж физических целей

Пространственный арбитр на серверном уровне учитывает изменяемые области в координатах измерения и владельца цели. При принятии или изменении проекта несовместимое пересечение с другой активной целью отклоняется до создания материальных обязательств. Для стройки, ремонта и разбора одного здания допускается явная последовательность под одним владельцем, но не независимые противоположные цели. То же правило действует для участков добычи и иных планируемых изменений блоков; оно не ограничивается одной колонией.

Область и ревизия владения принадлежат цели, а не назначенному жителю. Расширение области проходит новый арбитраж; перед каждым изменением исполнитель проверяет актуальность владения. Ожидание и перепланирование не передают участок другому владельцу автоматически. Завершение или безопасная отмена освобождают область после прекращения её физических действий. После загрузки владение восстанавливается до возобновления работ, конфликтующие цели блокируются с диагностикой. Проверки пересечений порционные, финальное предоставление права выполняется с повторной проверкой ревизии без уступки; объём областей и связей индекса ограничен допуском (§6.5). Это координация целей Colonyloom, не блокировка целого чанка, не запрет действий игрока и не замена внешних прав или сверки мира.

## 13. Загрузка чанков

Территориальная принадлежность, загрузка и готовность к тикам сущностей — разные состояния.

```text
ChunkDemand
  colonyId
  dimension / chunk
  owner / reason
  requiredReadiness
```

Менеджер требований находится на серверном уровне. Он объединяет пересечения и удерживает чанк, пока есть хотя бы одно допущенное требование: населённая область, рабочее здание, стройка, нужный маршрут или временная операция. Зарегистрированное желание загрузки не равно допуску и не создаёт билет автоматически.

Житель не владеет бессрочным билетом на каждый когда-либо посещённый чанк. Планируемый путь также не вызывает неограниченную загрузку исследуемых кандидатов.

Устанавливаются серверный предел одновременно удерживаемых чанков по уровням готовности и доли колоний; пересечения учитываются один раз в глобальном пределе. Учитываются также необходимые соседние чанки, если API загрузчика удерживает их для требуемой готовности. Все требования проходят допуск независимо от скорости их поступления. Постепенное создание удалённых зданий не позволяет обойти суммарный предел.

Новая работа вне допущенной области остаётся в ограниченном ожидании лимита либо отклоняется до начала физических действий. Маршрут не направляет жителя в неготовую область. За пределами активной области нет фиктивного физического производства; положение и имущество не заменяются логическим продолжением работы. Уже оказавшийся вне неё житель не пересоздаётся и получает ограниченную операцию возврата/восстановления в рамках выделенной служебной доли.

Временные требования снимаются после операции; постоянное удержание рабочего здания действует только пока оно включено в допущенную активную область. Уменьшение лимита не обрывает перенос и не теряет груз: новые допуски останавливаются, выполняется безопасное сворачивание операций, затем освобождаются билеты. До завершения сворачивания превышение нового лимита явно показывается; мгновенное достижение уменьшенного предела не обещается. При запуске все требования снова проходят допуск.

Допуск пересматривается не только при появлении свободного места, но и при блокировке зависимости активной работы. Исходная политика — безопасно выводить из допуска незанятые некритические области ради необходимых зависимостей с учётом приоритета и возраста ожидания. Заявка здания сохраняется, но не даёт бессрочного права удерживать билет. Сворачивание сначала прекращает новые действия и безопасно размещает текущие грузы; область с незавершённым физическим шагом не вытесняется вслепую. Служебная доля также используется для сверки и возврата, но входит в общий предел.

Если последовательная смена областей вмещает рабочее множество разрешимой операции, политика должна обеспечивать её продвижение без ручной отмены несвязанных целей. При недостаточном минимальном рабочем множестве, отсутствии безопасного вытеснения или внешнем запрете показывается соответствующая блокировка. Например, при допущенных получателе A и незанятой мастерской C сохранённый курьер в B не должен бесконечно ждать C: после безопасного снятия её допуска проверяется B и продолжается доставка. Неизвестный груз при этом не объявляется утраченным.

### Неактивные жители и время

Неактивность — явное состояние допуска жителя, а не вывод из отсутствия загруженной сущности. Переходом управляет серверный runtime: обычные назначения прекращаются, имущество и незавершённые эффекты остаются под сверкой/восстановлением, а новая физическая работа невозможна до повторного допуска и готовности зависимостей. Дом и другие долгосрочные назначения сохраняются и продолжают занимать свою вместимость; неактивный житель не считается свободным работником.

Исходная политика — пауза собственного активного времени: голод, усталость, возраст и прогресс болезней, которыми владеет Colonyloom, не накапливаются за период неактивности. Сохраняются текущие значения и остатки сроков; таймеры не остаются привязаны к старому серверному дедлайну. При возвращении нет догоняющего потребления, производства или старения, текущая фаза суток выбирается заново, пробуждения распределяются по тикам. Уже наступившая потребность не сбрасывается. Пауза действует только для недопущенного жителя, не для обычного ожидания работы, дефицита еды или сна; она не является произвольной командой игрока. Допуск не отключает физические события Minecraft: если сущность всё же тикает из-за игрока или другого владельца чанка, урон, смерть и изменение имущества обрабатываются как реальные факты. Мост здоровья не дублирует их собственным таймером.

### Восстановление и ограничения

- Новые запросы загрузки распределяются по тикам.
- После запуска требования пересчитываются из активного состояния.
- Билет не считается доказательством готовности; работа ждёт нужного уровня доступности.
- Удаление операции снимает её требование, но не требования других владельцев.
- Ошибка загрузки становится видимым ожиданием с ограниченной повторной попыткой.
- Конкретные размеры лимитов и правила выбора постоянно активных областей фиксируются до допуска целевой нагрузки (§24); обязательность суммарного предела и поведение отказа закреплены здесь.

**Постоянно загруженные чанки тикают не только Colonyloom.** Редстоун, фермы, мобы и другие моды создают нагрузку, которую бюджет нашего планировщика не отменяет. Поэтому масштаб задаётся числом жителей, активных чанков и интенсивностью работ одновременно.

## 14. Игровые системы поверх ядра

### Потребности и расписание

Питание, отдых, здоровье и безопасность изменяют доступность исполнителя. Пороговые изменения пробуждают нужную логику. Собственные таймеры следуют активному времени и переходам неактивности (§13), а фаза дня — игровым суткам. Точные правила совместимости работы и удовлетворения потребности задаёт gameplay, а не платформенный адаптер.

### Профессии и производство

Профессия определяет допустимые работы, важные навыки, инструменты и доступные процессы. Производственный заказ содержит рецепт, оборудование, ингредиенты и проверяемый результат. Повышение уровня здания меняет возможности через явные правила, а не условие по загрузчику.

### Образование и исследования

Разделяются личное развитие жителя и общеколониальные исследования. Исследование имеет требования, стоимость, прогресс и эффекты. Открытие исследования не запускает полный пересчёт каждого работника: инвалидируются соответствующие производные возможности.

### Болезни, смерть и восстановление

Смерть снимает назначение и изменяет жизненный цикл жителя. Реальный инвентарь обрабатывается выбранной механикой смерти. Медицинская помощь, сбор имущества и специальное восстановление — разные работы. Выгрузка сущности не запускает эти процессы.

### Оборона

Подсистема угроз задаёт тревогу и приказы. Боевые исполнители выполняют физический бой через Minecraft. Приоритет угрозы не позволяет обойти ограничения доступа или изменить колониальные записи с чужого потока.

### Квесты

Квест игрока наблюдает подтверждённые факты: завершена стройка, доставлен предмет, закончено исследование. Он не завершает рабочие заказы прямой записью в чужое состояние. Выдача награды — отдельная проверяемая операция.

Цель-предикат проверяет текущее состояние мира или колонии. Историческая цель («доставить после принятия квеста») использует сохраняемый предметный счётчик с областью получателя/игрока и исходной отметкой при принятии либо ограниченные свидетельства с ID операций, если одного счётчика недостаточно. Текущий инвентарь не доказывает прошлую доставку. Источник факта, граница отсчёта, прогресс цели и отдельное состояние выдачи награды определяются до реализации типа квеста (§17.4, §18.1).

## 15. Контракты интеграции и несколько загрузчиков

Проектные границы, не утверждённые сигнатуры:

| Контракт | Назначение | Обязательный смысл результата |
|---|---|---|
| `WorldAccess` | Проверки мира и ограниченные действия с контекстом полномочий | Фактический результат, отказ в доступе, неподдерживаемость или недоступность |
| `StorageAccess` | Каноническая идентичность запаса, чтение и переносы с контекстом полномочий | Пересечения представлений, реальное количество, оставшийся объём и явная причина отказа/неподдерживаемости |
| `NavigationService` | Запрос и отмена маршрута | Связь с целью и актуальностью |
| `ChunkAccess` | Требования готовности чанков | Различие запроса, загрузки и пригодности |
| `PersistenceStore` | Сохранение и чтение схем | Версия, ошибки, граница подтверждения |
| `NetworkTransport` | Доставка сообщений | Не принимает решения за симуляцию |

Не абстрагируется каждый ванильный тип. Общая Minecraft-интеграция использует ванильные API напрямую там, где они одинаковы. В `core` передаются собственные ограниченные значения и результаты, а не копия всей объектной модели Minecraft.

Адаптер загрузчика реализует реальные различия: регистрация, события, билеты чанков, транспорт, платформенные API хранилищ и конфигурация. Игровая логика не содержит `isFabric()` / `isNeoForge()`.

Первый поддерживаемый вариант — Minecraft 1.21.1 + NeoForge. Для каждого последующего загрузчика или версии игры отдельно фиксируются поддерживаемая пара, зависимости и формат поставки. Несколько загрузчиков и версий не означают единый универсальный JAR, бинарную или сетевую совместимость произвольных сборок. Совместимость протокола, контента и сохранений проверяется отдельно. Одна и та же проверка игрового сценария выполняется на каждой объявленной поддерживаемой паре; будущие пары не блокируют первый этап.

### 15.1. Субъект отложенного действия

Контекст операции содержит колонию, исполнителя, вид действия, цель, режим полномочий и инициатора, если он есть. Запрос игрока проверяется при приёме, но не выдаёт бессрочное разрешение на будущие изменения. `WorkOrder.owner` обозначает владение работой и не заменяет субъект авторизации.

Индивидуальная операция игрока сохраняет его ID и повторно проверяет его текущие права. Принятая колониальная цель, включая стройку, и автономная работа исполняются от имени колонии; инициатор сохраняется для происхождения команды, но его прежние права не используются. Для внешней защиты субъектом колонии служит её текущий владелец, а NPC передаётся как исполнитель, не как привилегированный администратор. Смена владельца меняет применимый субъект; отсутствие разрешённого субъекта блокирует действие. Отзыв прав инициатора сам по себе не отменяет уже принятую колониальную цель.

Проверки текущих внутренних и внешних прав выполняются непосредственно перед чтением защищённых данных или физическим изменением, включая изъятие, передачу и бой. Адаптер не подменяет невозможность выразить контекст обходом защиты: при неподдерживаемом контракте возвращается явная неподдерживаемость или отказ. Конкретные claims/protection-интеграции выбираются отдельно, но обязаны соблюдать эту семантику.

## 16. Расширяемость и определения контента

### 16.1. Данные и код

Через данные задаются рецепты, числовые параметры, исследования, требования, чертежи, состав зданий, простые цели квестов и профессии на существующем поведении.

Через код добавляются новые способы работы: необычная машина, новый тип движения, специальная боевая механика или новый физический процесс.

```text
Регистрация расширения
  → стабильный typeId
  → схема определения
  → схема сохраняемого состояния
  → обработчик
  → миграции при изменении формата
```

Штатный контент использует те же предметные регистрации. Это не обещание горячей выгрузки исполняемого кода или песочницы для стороннего мода.

### 16.2. Загрузка и ошибки

Перед активацией проверяются ссылки, типы, обязательные поля и зависимости. Удалённый тип не заменяется другим молча. Сохраняемые данные неизвестного типа не уничтожаются; затронутый объект блокируется с диагностикой, а связанные работы получают явную недоступность.

Определения читаются как согласованный набор. Reload не должен позволять половине колонии работать со старым рецептом, а другой половине — с новым в пределах одной операции. Точная политика смены определений при активных работах фиксируется до реализации reload.

### 16.3. Граница доверия

Расширение на Java внутри того же процесса не является изолированным. API задаёт поддержанный путь интеграции, но не защищает сервер от произвольного вредоносного кода другого мода.

## 17. Хранение, миграции и восстановление

### 17.1. Три вида данных

| Вид | Примеры | Политика |
|---|---|---|
| Определения | Профессии, рецепты, чертежи | Версии контента и стабильные IDs |
| Долговременное состояние | Жители и привязки, активное время и остатки сроков, здания, работы и области целей, обязательства и выделения снабжения, исследования, прогресс квестов и свидетельства фактов | Версионированные схемы и миграции |
| Производные данные | Индексы, маршруты, кеши | По возможности восстановление вместо сохранения |

Хранение находится в данных мира. Собственная внешняя БД не выбрана. Конкретные Minecraft storage API и раскладка файлов определяются после выбора версии.

Рабочие объекты не сериализуются автоматически. Сохраняются цель, этап, подтверждённый прогресс и связи, а не callback, поток, стек вызовов или ссылка на инвентарь.

### 17.2. Последовательность загрузки

```text
Чтение и проверка версий
  → миграции
  → восстановление идентичности и связей
  → построение необходимых индексов
  → постепенный запрос чанков
  → сверка с миром, сущностями и инвентарями
  → постепенное возобновление работ
```

Это порядок зависимостей, а не барьер готовности всей колонии. Восстанавливаемые объекты и обязательства имеют runtime-состояния `Unknown`, `Reconciling`, `Ready`, `Blocked`. До сверки неизвестность не трактуется как пустой инвентарь, потерянный груз или смерть. Сохранённые покрытие и выделение у потребителя в неизвестном состоянии не снимаются автоматически и не разрешают повторно заказать тот же объём.

Работа допускается к продолжению после сверки необходимых именно ей записей, воплощения жителя, этапа, пространственного владения и хранилищ с канонической привязкой запасов. Несвязанные работы в готовой области продолжаются, даже если один чанк недоступен. Ожидание допуска зависимости запускает безопасный пересмотр активных областей (§13). Если после этого зависимость нельзя проверить в рамках допуска или она повреждена, показывается `Blocked` с причиной; дальнейшее решение принимает предметная политика восстановления, не догадка об отсутствии ресурса.

Повреждённое состояние не превращается молча в новую пустую колонию. До деструктивной миграции требуется возможность восстановить исходные данные. Обновление схемы не означает автоматическую поддержку downgrade.

### 17.3. Остановка

Runtime прекращает приём новых работ, завершает текущие допустимые атомарные шаги и сохраняет согласованный снимок своих данных. Физические долгие процессы не обязаны закончиться до остановки: их продолжение представлено сохраняемым этапом.

До снимка собственных данных подтверждённые предметные факты представлены сохраняемым состоянием источника: счётчиком или свидетельством операции. Отложенная обработка квеста не оставляет единственное свидетельство в оперативной очереди событий. Это не делает снимок колонии атомарным с сохранением мира.

Фоновые результаты после остановки или смены runtime-generation не применяются.

### 17.4. Граница атомарности

Мир, сущности, инвентари и данные колонии не являются одной атомарной транзакцией. Простое добавление журнала работ не даёт exactly-once для физического мира.

Проверка «блок уже установлен» предотвращает часть повторов, но не доказывает, что материалы были списаны ровно один раз при аварии между независимыми сохранениями.

Для переноса, крафта, установки блока, смерти и награды нужна собственная политика восстановления и испытания в точках прерывания. Пока они не выбраны, отсутствие любых потерь и дублирования при аварийном завершении не обещается. Контролируемое промежуточное хранение, если потребуется, проектируется отдельно, а не вводится как фиктивная универсальная транзакция.

**Барьер проектирования:** до реализации первого сохраняемого эффекта каждого типа фиксируются независимо сохраняемые стороны, точки прерывания, доступные свидетельства, правила повторного исполнения, допустимые потери/дублирование и способ обнаружения неоднозначности. Требуемые ID операций, этапы или промежуточное хранение входят в формат сразу. Штатное сохранение и хотя бы одно прерывание проверяются в первом вертикальном срезе; полная матрица отказов не откладывает выбор политики.

Если свидетельств недостаточно, операция блокируется для предметной сверки или явного административного решения, а не безусловно повторяет выдачу или списание. Это консервативное поведение не гарантирует отсутствие уже случившегося расхождения. Пока политика конкретного эффекта не определена, он не считается готовым к включению в сохраняемую экономику. Очистка свидетельств и маркеров удаления возможна только после закрытия зависимостей и установленной границы безопасного удаления; до этого объём учитывается в допуске состояния (§6.5).

## 18. События и наблюдаемость

### 18.1. Команды и факты

Команда просит изменить состояние. Событие сообщает об уже подтверждённом изменении. Уведомление не даёт получателю права переписать состояние другого владельца.

Локальные события содержат достаточные IDs, scope и ревизию. Синхронный рекурсивный каскад обработчиков не используется как планировщик всей экономики. Изменения ставят ограниченную работу в соответствующую очередь.

Уведомления об инвалидации могут объединяться с сохранением необработанной ревизии и `dirty/pending` по §6.3. Фактические результаты предметных операций и начисления наград не сворачиваются как взаимозаменяемые сигналы. Проекция текущего состояния пересобирается из авторитетных записей. Историческая проекция восстанавливается только из сохраняемого счётчика или свидетельств источника (§14), а не из текущего наличия предметов.

Фиксация подтверждённого результата в собственном состоянии runtime включает обновление его исторического источника до публикации уведомления. Повторное применение одного свидетельства к потребителю не увеличивает прогресс второй раз: учитывается ID операции или исходная/применённая отметка счётчика. Свидетельства ограничены по объёму и очищаются после подтверждения потребителей и закрытия восстановительных зависимостей; переполнение останавливает допуск новых эффектов, а не теряет факты. Согласование с независимо сохранённым физическим результатом остаётся предметной политикой §17.4.

Durable replay всех событий, глобальный exactly-once и бесконечная история не выбраны.

### 18.2. Метрики

- Время подсистем за тик и распределение длинных тиков; отдельно тики сущностей, движение, столкновения, бой и последствия изменений блоков.
- Длины очередей, возраст готовой работы, задержки критических цепочек и нарушения их сроков.
- Число и стоимость поисков пути, доля устаревших результатов; при иерархии — построение, обновление и память графа.
- Число обращений к инвентарям, просмотренных слотов, стоимость сверок, возраст индекса и задержка обнаружения поступлений.
- Допущенные и ожидающие чанки по уровням готовности, сущности и операции строительства.
- Объём сетевых снимков и изменений.
- Выделения памяти, размер кешей, узлов/рёбер графа, обязательств и исторических свидетельств; достижение лимитов и отказы в допуске.
- Заполнение критического резерва, сворачивание фронтов и продвижение при полном лимите; число проверок атомарного комплектования; возраст `dirty/pending`, задержка смены активных областей и число неактивных жителей.
- Время сохранения, загрузки и миграций.

**Стабильный TPS при бесконечно растущей очереди не считается успехом.**

Горячий цикл не пишет строковый лог на каждый шаг. Подробная трассировка ограничена выбранной колонией/работой и временем наблюдения; агрегированные счётчики не требуют постоянного выделения объектов.

## 19. Сеть, UI и границы авторитета

### 19.1. Команды

Клиент передаёт намерение: построить, назначить, изменить приоритет, начать исследование, изменить права. Сервер проверяет отправителя, принадлежность, разрешения, диапазоны значений, актуальность объекта и условия выполнения.

Наличие открытого окна или известного ID не является разрешением. Сетевые данные имеют ограничения размера и количества; сообщения не запускают неограниченный скан колонии.

Повторная отправка команды с расходом ресурсов не должна считаться безопасной автоматически. Политика идентификаторов запросов, подтверждений и разрешения неизвестного результата определяется в протоколе.

### 19.2. Подписки

| Открытая поверхность | Передаваемые данные |
|---|---|
| Ратуша | Агрегированная сводка и выбранная страница |
| Здание | Состояние конкретного здания и связанных работ |
| Житель | Подробности выбранного жителя |
| Очередь | Ограниченная страница с нужной сортировкой |
| Карта | Необходимая область и уровень детализации |
| Физические сущности рядом | Стандартное отслеживание плюс нужные данные мода |

Используются начальный снимок и изменения с ревизиями. При пропуске или несовместимой ревизии клиент запрашивает новый ограниченный снимок. Медленный клиент не удерживает неограниченную очередь и не блокирует симуляцию.

Первичная подписка и каждый запрос повторного снимка проверяют право чтения и доступную область данных, независимо от известного ID. Подписка связана с ревизией полномочий. При изменении состава колонии, ранга или владельца она переавторизуется либо снимается до следующей передачи; уже подготовленные, но ещё не отправленные сообщения со старой ревизией отбрасываются или формируются заново после проверки. Отозвать уже переданные клиенту сведения невозможно: гарантия относится к последующим выдачам сервером.

Агрегаты обновляются реже физического состояния. Всем игрокам не рассылаются все жители, работы и инвентари каждый тик.

### 19.3. Клиентский код

Клиентские классы, рендереры и экраны изолированы от загрузки на dedicated server. Предпросмотр и анимация не совершают авторитетные изменения мира.

## 20. Сквозной пример: строительство из произведённых материалов

Пример показывает взаимодействие подсистем, а не готовый API.

1. Игрок размещает проект. Сервер проверяет права, определение здания, допустимость цели, отсутствие несовместимого пространственного пересечения и лимит состояния с сохранением критического резерва; фиксирует колониальный режим полномочий и инициатора.
2. Создаётся `ConstructionSite` и строительная работа с областью и ревизией пространственного владения. Чертёж разделяется как неизменяемый ресурс. Требования чанков проходят допуск; до готовности области физических действий нет.
3. Анализ ближайшего участка обнаруживает потребность в ступенях.
4. `SupplyPlanner` вычитает исполненную часть цели, выделение у потребителя и активное покрытие; только для непокрытого остатка проверяет индекс и реальные источники. Готовых ступеней нет.
5. Выбирается плотник с подходящим рецептом. В пределах графового лимита создаётся заказ или доля общей партии, регистрируется покрытие ступеней и потребности в досках/брёвнах. Повторный проход не заказывает этот объём заново; при заполнении графа незапущенные фронты сворачиваются ради продвижения выбранной исполнимой ветви.
6. Источники подбираются порционно с учётом канонического запаса. Ограниченный набор позиций повторно проверяется и полный комплект резервируется одним шагом арбитража. Курьер получает доставку, допустимый маршрут и путь безопасного размещения при отказе получателя.
7. При извлечении проверяются актуальные полномочия и реальный инвентарь. Если игрок забрал часть комплекта, подтверждается только фактическое количество, лишние резервы освобождаются, полученный груз безопасно размещается до нового комплектования.
8. Производитель получает выделенные ингредиенты, выполняет процесс и подтверждает расход и реальный результат по предметной политике. Покрытие ступеней переходит от обещанного выхода к реальным предметам без двойного учёта.
9. Ступени доставляются строителю. Подтверждённая передача одновременно уменьшает покрытие и увеличивает выделение у потребителя; отдельный исторический факт фиксируется в сохраняемом источнике до уведомления квестов. Утрата до расхода после сверки снимает соответствующее выделение и вновь открывает дефицит, не откатывая историю доставки.
10. Строитель перед каждым действием проверяет мир, пространственное владение, материалы, готовность чанка и текущие права субъекта колонии. Подтверждённый расход переводит выделение в исполненную часть потребности, а результат продвигает участок по выбранной восстановительной политике.
11. Завершение работы снимает ожидания и лишние резервы, освобождает неиспользованные выделения, закрывает её доли общих заказов и пространственное владение после прекращения действий, снимает временные требования чанков и обновляет только разрешённые подписки UI.

### Прерывания

| Событие | Требуемое поведение |
|---|---|
| Нет сырья | Объяснимое ожидание, без повторного полного планирования каждый тик |
| Путь перекрыт | Ограниченный пересчёт, задержка повторной попытки |
| Курьер погиб | Груз определяется реальным состоянием имущества; доставка не объявляется успешной |
| Игрок отменил стройку | Новые действия её доли прекращаются; другие потребители общей партии сохраняются; уже построенное, груз и излишки обрабатываются отдельно |
| Игрок поставил целевой блок | Строитель сверяет цель, не повторяет действие и уменьшает оставшуюся материальную цель с обработкой лишнего выделения/покрытия, не записывая фиктивный расход |
| Чанк ещё не готов | Работа ждёт; наличие билета не подменяет проверку |
| Получатель заполнен | Груз безопасно размещается, курьер и его вместимость освобождаются; если это невозможно, показывается блокировка вместимости и ограничиваются новые доставки |
| Исчерпан предел чанков или графа | Без роста сверх допуска пересматриваются активные области или сворачиваются незапущенные фронты ради разрешимой цепи; недостаточное рабочее множество показывается как блокировка ёмкости, не отсутствие рецепта |
| Изменились полномочия | Перед следующим действием проверяется актуальный субъект; подписки без права чтения прекращаются |
| Сервер штатно перезапущен | Неизвестный груз не считается потерянным; каждая работа ждёт сверки своих зависимостей, независимая готовая работа продолжается |
| Авария между изменениями | Применяется предметная политика восстановления; универсальный rollback не обещан |
| Утрачен материал после доставки | Сверка уменьшает выделение, открывает дефицит только на утраченную долю и сохраняет исторический факт доставки |
| Принята конфликтующая физическая цель | Арбитраж отклоняет пересечение до новых обязательств; устаревшее владение запрещает последующие действия |
| Житель не допущен к активной симуляции | Собственные часы и остатки сроков приостановлены; физические факты не игнорируются, возврат не создаёт догоняющих расходов |

## 21. Проверка архитектуры и производительности

### 21.1. Уровни проверки

- Изолированные проверки `core`: переходы, зависимости, назначения, резервы и бюджеты.
- Интеграционные проверки в Minecraft: настоящие инвентари, блоки, сущности, чанки и сохранения.
- Один и тот же игровой сценарий на каждой поддерживаемой паре версии игры и загрузчика; сначала только Minecraft 1.21.1 + NeoForge.
- Dedicated server: отсутствие загрузки клиентских классов.
- Нагрузочный прогон в реальном мире с выбранным контентом и настройками.

Заглушка инвентаря не доказывает совместимость со сторонним хранилищем. Unit tests планировщика не доказывают стоимость навигации Minecraft.

### 21.2. Минимальные проверки контрактов

| Проверка | Что должно подтверждаться |
|---|---|
| Две независимые колонии | Обычная работа не сканирует и не изменяет ресурсы другой |
| Два потребителя одного запаса | Нельзя обещать доступное количество дважды |
| Игрок изменил инвентарь | Реальный перенос корректирует резерв и остаток |
| Частичная доставка | Ровно переданное количество переходит из покрытия в выделение либо исполнение цели доставки; до расхода производственной цели оно не считается исполненным |
| Цикл рецептов | Конечная диагностика неразрешимой ветви без зависания; доступный исходный запас или разрешимая альтернативная ветвь не отвергаются из-за самого наличия цикла |
| Отмена с грузом | Предметы не исчезают вместе с логическим заказом |
| Устаревший маршрут | Новая цель не получает результат старого запроса |
| Пересекающиеся требования чанка | Снятие одного владельца не выгружает нужный другому чанк |
| Неизвестный тип контента | Данные сохраняются, проблема видима, нет молчаливой подмены |
| Поэтапный перезапуск | При незагруженном курьере его груз остаётся неизвестным, покрытый объём не заказывается повторно; работа без этой зависимости продолжает исполнение |
| Неполномочный клиент | Команда отклонена до предметного изменения |
| Медленный клиент | Нет неограниченного накопления сообщений |
| Перегрузка | Сохраняется прогресс разных колоний, возраст очередей наблюдаем |
| Повторное планирование покрытой потребности | Во время производства, перевозки и после частичной передачи новый заказ создаётся только на непокрытый остаток; переход стадий не удваивает покрытие |
| Конкуренция комплектов | Два ациклических заказа требуют X и Y, запас достаточен для одного: хотя бы один получает полный комплект и продвигается; второй не удерживает его недостающую часть |
| Внешняя утрата части комплекта | Остальные неиспользованные резервы освобождаются, полученный груз сохраняется и безопасно размещается, повторное комплектование не создаёт фиктивный запас |
| Отмена доли общей партии | Отмена A до и после начала партии для A и B не отменяет долю B; лишние резервы снимаются, неизбежный излишек имеет реальное назначение |
| Полный получатель и один курьер | При наличии доступного места возврата/промежуточного размещения курьер освобождает грузовую вместимость, вывозит продукцию и устраняет блокировку; при отсутствии места виден отдельный отказ вместимости, груз не исчезает |
| Постепенное расширение территории | Медленное добавление удалённых работ не превышает суммарный допуск чанков; пересечения, соседние чанки готовности и доли колоний учтены |
| Снижение лимита чанков | Новые допуски прекращаются, текущий груз сохраняется, временное превышение видно до безопасного освобождения билетов; рестарт не обходит новый допуск |
| Широкий ациклический граф | Общий предел узлов/рёбер и заказов соблюдается между тиками; ожидание лимита не объявляется отсутствием рецепта; отмена и освобождение выполняются даже при заполненном лимите |
| Кеш долгоживущего владельца | Рост уникальных запросов ограничен размером кеша и суммарным пределом, не только моментом уничтожения владельца; вытеснение не меняет авторитетное состояние |
| Старое или дублированное воплощение | Поздно загруженная старая эпоха, сущность без записи и конфликт UUID не получают назначения/доступного снабжению инвентаря; имущество не удаляется и не выдаётся повторно |
| Историческая цель квеста | Доставленный и затем израсходованный предмет учитывается после сохранения до обработки уведомления; повторное применение свидетельства не увеличивает прогресс; факты до принятия цели не засчитываются |
| Прерывания физических эффектов | В выбранных точках переноса, крафта, блока, смерти и награды выполняется заранее определённая политика; неоднозначность блокируется, а не скрывается безусловным повтором |
| Субъект отложенного действия | После смены владельца или отзыва прав индивидуального инициатора проверяется актуальный субъект; автономная работа не обходит внешнюю защиту, неподдерживаемый контекст даёт отказ |
| Отзыв права чтения | Подписка по известному ID и повторный снимок без доступа отклоняются; отзыв прав прекращает последующие выдачи, включая подготовленные, но не отправленные данные |
| Критическая цепочка при перегрузке | В принятом профиле питание/реакция на угрозу и их зависимости укладываются в выбранные сроки, обычные категории продвигаются; сверх профиля ограничивается допуск и видны нарушения |
| Поступление без уведомления | Ограниченная сверка обнаруживает предмет во всех допущенных хранилищах в пределах выбранного возраста индекса и пробуждает потребность; горячие хранилища не вытесняют остальные |
| Утрата после передачи до расхода | Из 64 доставленных единиц 16 утрачены: новый дефицит равен 16, а не 0 или 64; подтверждённо израсходованное не заказывается вновь, историческая доставка сохраняется; Unknown после рестарта не считается утратой |
| Два представления одного запаса | Через стороны/обёртки, включая регистрацию в разных колониях, суммарно резервируется не больше общего доступного количества; неизвестное тождество явно не поддерживается, замена контейнера требует новой сверки |
| Конкурирующие фронты при полном графе | При двух цепях глубины три и четырёх доступных узлах фронты A0,A1,B0,B1 не остаются вечным тупиком: один незапущенный фронт сворачивается и другая цепь доходит до листа, затем продвигается ожидавшая; компактные цели и служебное состояние учтены отдельно в общем допуске |
| Новая критическая потребность после насыщения | Обычные задачи заполняют всю разрешённую им ёмкость; возникшая потребность в доступной еде и её доставка создаются в критическом резерве и исполняются без ручной отмены строек; лимиты не превышены |
| Пересекающиеся физические цели | Разные блоки в одной координате, ремонт против разбора и добыча против стройки не исполняются как независимые противоречащие цели; отказ предшествует обязательствам, отмена/перезапуск сохраняют корректное владение |
| Зависимость в недопущенной области | При полном допуске A+C безопасное снятие незанятой C позволяет сверить курьера в B и продолжить доставку в A; неизвестный груз не дублируется, минимально невмещаемая цепь получает явную блокировку |
| Долгая неактивность жителя | При работающем сервере собственные значения и остатки сроков сохраняются без накопления голода/старения; уже возникший голод не сбрасывается, жильё остаётся занятым, физическая смерть учитывается; после допуска нет догоняющего расхода и массовой просрочки старых дедлайнов |
| Дорогой подбор одной партии | Множество грубо подходящих источников с неподходящими компонентами обходится порционно; финальный атомарный шаг не превышает лимита проверок/внешних вызовов и не расширяет поиск при устаревании кандидата |
| Пробуждение при заполненной очереди | Изменение между проверкой и регистрацией ожидания, переполнение очереди и повторная инвалидация во время обработки не теряют `dirty/pending`; работа получает повторную проверку после освобождения бюджета без нового внешнего события и без бесконечного роста очереди |

### 21.3. Нагрузочные сценарии

1. Несколько сотен жителей в обычной экономике.
2. Несколько одновременных больших строек.
3. Дефицит общего материала и его массовое поступление.
4. Изменение дороги и складских запасов игроком.
5. Рейд и одновременная смена намерений населения.
6. Рассвет и переход к ночному расписанию.
7. Запуск сервера с развитыми колониями.
8. Несколько одновременно открытых управленческих интерфейсов.
9. Отмена работ, смерти и загрузка/выгрузка при активных доставках.
10. Изолированная стоимость жителей без экономического планирования: покой, массовое движение, столкновения и доступный бой; сравнение с базовым миром без жителей.
11. Удерживаемые чанки с разной насыщенностью мобами, фермами и редстоуном; строительство с последствиями обновления блоков, а не только подсчётом установок.
12. Сравнение локального backend и кандидата с общим графом на изменяемой территории: создание/обновление графа, память, снимки, неуспешные и устаревшие запросы. Если иерархия не реализуется, сравнение не объявляется выполненным и её выигрыш не предполагается.
13. Много хранилищ и слотов, включая реальные поддерживаемые сторонние API, с поступлениями без уведомлений: стоимость сверки и задержка обнаружения измеряются вместе.
14. Длительная нагрузка сверх допуска: широкие графы, новые работы, удалённые стройки, заполненные получатели и критические потребности одновременно; размеры состояния ограничены, отказ допуска объясним, принятые операции можно завершить или безопасно отменить.
15. Насыщение обычного допуска с последующим возникновением критических потребностей; конкурирующие графовые фронты, смена областей для сохранённого груза и переполнение очереди пробуждений. Измеряется продвижение без ручного вмешательства, а не только ограниченность структур.

В отчёте фиксируются оборудование, версии, загрузчик, конфигурация, число колоний/жителей/чанков, состав активных работ и длительность прогона. Измеряются время тика, хвосты распределения, задержка работ, очереди, память и сеть.

Первое воспроизводимое измерение проводится на минимальном физическом исполнителе до сквозной экономики (§22). По нему фиксируются исходные числовые бюджеты, пределы состояния и профиль допустимой нагрузки со сроками критических цепочек и возрастом индексов. До полного нагрузочного прогона устанавливаются критерии приёмки: время тика и хвосты, задержки, пределы памяти/очередей и отсутствие ресурсных блокировок в разрешимых сценариях. Их изменение оформляется как пересмотр профиля, а не подгонка после прогона. Наличие планировщика не доказывает достижение 20 TPS.

## 22. Порядок реализации и критерии завершения

Порядок проверяет архитектурные границы до масштабирования контента. Он не отменяет функциональные области §2.

| Этап | Наблюдаемый результат |
|---|---|
| Платформа и сборка | Общая игровая часть запускается на Minecraft 1.21.1 + NeoForge, в клиенте с integrated server и на dedicated server; используется JDK 21 (64-bit) |
| Идентичность и lifecycle | Колония, здание и житель переживают сохранение; проверены единственная привязка, эпоха воплощения, конфликт дубликатов и незагруженная сущность |

| Работы и физическое действие | Назначенный житель достигает цели, выполняет реальное действие, ждёт или отменяется; проверены пространственный арбитраж и пробуждение при переполнении, сохранение и одно прерывание подтверждают выбранную политику |
| Ранние измерения платформы | На минимальном исполнителе измерены покой, движение и доступный бой, локальная навигация, чанки и изменения блоков; выбран исходный профиль нагрузки и лимиты допуска, иерархия пути обоснована сравнением либо не вводится |
| Сквозная экономика | Склад → запрос → производство → доставка → строительство работают на реальных предметах; проверены покрытие и выделения после доставки, утрата до расхода, каноническая идентичность запасов, ограниченное комплектование и освобождение логистики |
| Прерывания и восстановление | Полная матрица дефицита, отмены общей партии, перекрытого пути, смерти, неактивности, смены допущенных областей и аварийных точек проверяет заранее выбранные предметные политики |
| Масштаб | Тот же сценарий выполняется с целевой нагрузкой; подтверждены прогресс при полном графе, критический резерв состояния, задержки цепочек, свежесть индексов и границы атомарных шагов, не только время тика |
| Расширение контента | Новые профессии и системы используют общие контракты без собственной параллельной логистики |

Завершённым считается поведение, а не набор интерфейсов или компилируемых модулей. Первый вертикальный срез должен включать сохранение, отмену и изменение мира, а не только беспрепятственное строительство.

Для каждого следующего типа физического эффекта барьер выбора восстановительной политики повторяется до изменения формата и API. Ранний нагрузочный барьер проверяет ограничения платформы до сложной экономики; полный профиль с готовыми игровыми системами проверяется повторно на этапе масштаба.

| Событийное пробуждение и планировщик | Выбраны регистрация с повторной проверкой и сохраняемый до обработки `dirty/pending`; без полного опроса экономики каждый тик |
| Глобальные бюджеты | Раздельные пределы вычислений и состояния, отдельная ёмкость новых критических цепочек и служебного восстановления; числа определяются ранними измерениями |
| Граф потребностей и резервы | Выбраны сворачивание незапущенных фронтов ради прогресса, отдельные покрытие/выделение/исполнение и порционный подбор ограниченного атомарного комплекта |
| Физические запасы | Каноническая идентичность и общий арбитраж пересекающихся представлений обязательны для автоматического снабжения |
| Конфликтующие физические цели | Несовместимые пересечения отклоняются либо сериализуются одним владельцем; пространственный арбитраж действует между колониями |
| Неактивные жители | Выбрана пауза собственных часов и сохранение остатков сроков без догоняющего потребления; реальные события Minecraft не отменяются |
| Навигация | Выбрана управляемая граница; backend измеряется, общий граф проходов вводится только при подтверждённой выгоде |
| Асинхронность | Только изолированные вычисления по снимкам; не обязательна для каждой системы |
| Контент через данные и код | Bounded JSON профессий/процессов и single-palette StructureTemplate NBT; reload публикует целиком проверенный набор, принятые работы сохраняют immutable pins. Новые gameplay типы проходят собственный cutover |
| Формат сохранения | Native SavedData DTO root schema 2, concrete 1→2 immutable backup; future root отказывает, unknown nested records сохраняются opaque с блокировкой зависимостей; downgrade только full-world rollback |
| Восстановление | Dependency readiness и operator inspect/bind/accept-world; typed transfer/craft/food/death evidence, source/drop UNKNOWN без replay/компенсации. Каждый новый эффект G/F требует отдельной политики до реализации |
| Исторические факты | Сохраняемые счётчики или ограниченные свидетельства; текущий инвентарь не заменяет историю |
| Авторизация | Явный субъект отложенного действия, повторная проверка текущих прав и отзыв подписок |
| Внешняя БД, event sourcing, брокер | Не выбраны |
| ECS, DI-framework, scripting framework | Не выбраны как обязательные зависимости |
| Structurize и другие зависимости MineColonies | Автоматически не заимствуются; нужна отдельная оценка |
| Публичный API расширений | Проектируется по реальным точкам расширения; стабильность пока не обещана |
