# Аудит slice: management / ActionContext / UI-network / needs

## Область, метод и обозначения

Проверены перечисленные файлы реализации, их интеграции, соответствующие исходники unit/GameTest/dedicated-client сценариев, определения профессий/процессов и локализации. Сопоставление выполнено с `docs/architecture.md` §§2, 6.1–6.6, 14, 15.1, 16, 19, 21.2, 22. **Ни build, ни lint, ни formatter, ни test/GameTest я не запускал.** Ссылки `путь:строки` ведут на диапазоны исходников. `[Статика]` означает прямо видимый код/исходник теста, не успешное выполнение; `[INFERENCE]` — ожидаемый эффект при нагрузке/сетевом злоупотреблении, который требует runtime-измерения. Оценки — человеко-дни; предпосылки указаны с каждым пунктом.

Severity P1/P2 для продуктовых пробелов отражает риск для предлагаемого игрового MVP, а не утверждение, что широкая карта §2 должна целиком входить в ранний вертикальный срез. Если не назван обязательный контракт, ниже явно указано «контента/потока нет; invariant не нарушен».

## Замечания

### P1 — В штатном пользовательском потоке отсутствует создание/найм жителя

- **Код:** `colonyloom-neoforge/src/main/java/io/github/kpuctajluk/colonyloom/neoforge/ColonyloomBrigadier.java:45-52` — единственный `citizen create` требует permission 2, рядом имеется лишь `citizen assign`; `IdentityPlatform.java:167-189` — реальное создание entity через core и identity binding; `colonyloom-core/src/main/java/io/github/kpuctajluk/colonyloom/core/command/ColonyCommands.java:103-124` — `createCitizen` вызывает `requireOperator`; `ManagementProtocol.java:17-55` — ни Recruit, ни Spawn/CreateCitizen command body; `ColonyScreen.java:187-191,456-459` — действия GUI не включают найм.
- **Архитектурный контракт:** §2 `docs/architecture.md:59-86` называет население, посетителей/найм, жильё и назначения. §22 `:938-960` считает завершённым наблюдаемое поведение, а не только интерфейсы. При этом §2 — функциональный охват, не обещание сразу отгрузить все перечисленные подсистемы.
- **Механизм/сценарий:** обычный игрок может открыть экран `colonyloom ui`, основать колонию, назначать профессии/рабочие места существующим гражданам и менять членство/строить, но не может легально для себя создать первого жителя. Единственный штатный creation path — operator command. Публичные user-facing management payloads не имеют body для найма/приглашения жителя. Dedicated needs/management fixtures создают жителей операторскими/permission-2 командами, поэтому их успешный сценарий не демонстрирует обычный пользовательский bootstrap.
- **Подтверждение:** `[Статика]`; исключён alternate recruit/spawn command и все варианты Body из найденного command tree и protocol. Тестовый setup-контекст также виден в `NeedsScenario.java:35-62` и `ManagementClientScenario.java:140-150` (fixture формируется вне обычной экранной модели).
- **Пользовательский эффект:** без администратора новую колонию нельзя заселить и начать обычное автономное поселение; MVP остаётся демонстрацией админски поставленного NPC, а не самостоятельным циклом игрока.
- **Рекомендация:** добавить явный пользовательский поток найма/приёма жителя с текущей проверкой OWNER/MANAGER, admission до spawn, валидацией позиции/чанка/коллизий, атомарным lifecycle+binding и страницей подтверждения/результатом. Не повышать полномочия менеджера на operator-only recovery/служебные команды. Добавить real-client тест без OP, capacity-denial и отказа spawn без частичного identity.
- **Оценка:** **4–7 ч.-дн.** Предпосылка: переиспользовать имеющиеся entity spawn, territory/position validation, `createCitizen` и admission reservation; оценка для простого прямого найма, не включает посетителей, жильё, детей, цену/таймер найма или анимацию.

### P2 — У подписок/повторного снимка нет собственного входного rate limit

- **Код:** `ManagementProtocol.java:11-14` содержит `COMMANDS_PER_SECOND=20`, но это применяется только в `ManagementSession.command` (`:107-120`); `ManagementSession.java:185-220` обрабатывает `subscribe` и resync, проверяет session/access и лимит 4 активных страницы, но отдельного token/window/частотного лимита не ведёт; `:350-370` немедленно отправляет `ViewClosed` по доступному соединению при каждом отказе. `ManagementNetwork.java:38-45` непосредственно диспетчеризует `Subscribe` в session.
- **Архитектурный контракт:** §19.1–19.2 `docs/architecture.md:791-814`: сетевые сообщения ограничиваются размером **и количеством**, медленный клиент не должен накапливать неограниченную очередь, каждый повторный snapshot переавторизуется.
- **Механизм/сценарий:** клиент, прошедший Hello, может часто слать неавторизованные subscriptions, превышение четырёх активных подписок, смены ID/resync. Состояние активных view действительно ограничено четырьмя и page preparation использует глобальный budget, однако rejected subscribe отправляет close-ответ каждый раз; один и тот же ID с `resync=true` удаляет/пересоздаёт подготовку. Для неавторизованных запросов response возникает до какого-либо command rate limiter. Возможное использование соединения для response amplification/лишней синхронной работы — `[INFERENCE]`; точный транспортный темп не измерялся.
- **Подтверждение:** `[Статика]` для отсутствия отдельного rate gate и немедленного close response; `[INFERENCE]` для эксплуатационного ущерба под flood. Это не неограниченный серверный map-growth: active subscriptions ограничены четырьмя, а deferred-closed map также ограничена.
- **Пользовательский эффект:** подключённый недоверенный клиент может генерировать сетевые close-ответы и повторно занимать management preparation service budget, воздействуя на общий серверный поток; лимит команд сам по себе это не ограничивает.
- **Рекомендация:** ограничить/дедуплицировать subscribe/resync/rejected-subscribe per session (включая повторные ошибки по одному ID), сохранить 4-view cap, ACK timeout, shared row budget и немедленную проверку прав. Проверить, что throttling invalid IDs не создаёт возможности удерживать старые view без обновления.
- **Оценка:** **1–2 ч.-дн.** Предпосылка: стандартная per-session sliding window/fixed token budget, без нового глобального traffic-control сервиса; добавить unit cases для burst, valid resync и close response dedup.

### P2 — Членство в колонии не имеет отдельного admission limit

- **Код:** `ColonyRuntime.java:8-20` копирует весь `members` в immutable map, но не проверяет размер; `ColonyCommands.java:78-93` клонирует и расширяет map при каждом `setMember`; `ColonyRegistry.java:89-102` ограничивает колонии/граждан отдельными admission leases, но не членство; `RegistryNbt.java:481-488,502-510` читает/пишет список участников; `ManagementViews.java:43-44,82-84,150-155` удерживает итератор по всем членам и порционно строит список.
- **Архитектурный контракт:** §6.5 `docs/architecture.md:305-312` требует ограничивать долговременный принятый объём состояния независимо от вычислений и отказывать до принятия новых обязательств. В §2 multiplayer — предусмотренная функция, а не единичные фиксированные роли.
- **Механизм/сценарий:** каждый `setMember` добавляет UUID в неизменяемый агрегат, без лимита на членов колонии/общее состояние. Персональная rate-limit сессии ограничивает скорость одного соединения, но не размер долгоживущего membership set; создание сводки просматривает членство, snapshot/NBT копирует его. Глобальные resource categories не содержат `MEMBERS`.
- **Подтверждение:** `[Статика]` для отсутствия member-specific admission и копирования/полного просмотра. Достижение NBT-файловой границы и конкретная стоимость — `[INFERENCE]`; другие persistence-ограничения не заменяют явную admission-проверку до мутации.
- **Пользовательский эффект:** накопленный набор участников может непропорционально увеличить копирование, сохранение и длительность агрегатного view; администратор не получает ясного штатного `MEMBER_LIMIT` до изменения.
- **Рекомендация:** определить допустимый max members на колонию и/или общий серверный cap; резервировать admission до immutable-map replacement, восстановление проверять на той же границе, показывать предел/занятость в management view и тестировать отказ без изменения authority revision/снимка.
- **Оценка:** **1–2 ч.-дн.** Предпосылка: продукт определяет конкретный предел; использовать существующую схему `SimulationLimits.Resource`/`AdmissionLedger`, включая NBT validation, без отдельной подсистемы членства.

### P2 — Проверка территории основания колонии синхронно сканирует до 16 384 позиций

- **Код:** `Territory.java:3-9` допускает ширину и глубину до 128 включительно; `IdentityPlatform.java:409-417` проверяет каждую пару X/Z циклом с `WorldBorder` и `mayInteract`; management route — `ManagementBackend.java:61-69` → `ColonyCommands.createColony`; capacity `COLONIES` равно 3 в `SimulationLimits.java:9-10,114-116`; команда проходит command budget per-session перед выполнением (`ManagementSession.java:107-121`).
- **Архитектурный контракт:** §6.2–6.5 `docs/architecture.md:265-312` требует глобально bounded quanta, уступки для дорогой работы и проверки ресурсов до принятия; §19.1 `:791-797` запрещает сообщениям запускать неограниченный скан.
- **Механизм/сценарий:** максимальная разрешённая территория даёт `128×128=16 384` синхронных физических вызова проверки прав. Core делает проверку overlap до physical scan, но при полной capacity новая неперекрывающаяся территория пройдёт этот scan и лишь затем может получить отказ admission в `ColonyRegistry.addColony`. Это не бесконечный цикл: работа ограничена размером территории. Однако она не делится на scheduler portions и не списывает global computation budget; управление запросом с нескольких client sessions суммируется сервером. Пиковый удар при concurrent/multiple clients — `[INFERENCE]`.
- **Подтверждение:** `[Статика]` максимальная геометрия и placement физического scan; `[INFERENCE]` заметная server-thread задержка/DoS при заполненном cap и нескольких запросчиках, runtime-стоимость не измерялась.
- **Пользовательский эффект:** большой ввод основания может блокировать server thread; повторные отклонённые попытки могут повторять дорогую проверку, даже когда колоний больше принять уже нельзя.
- **Рекомендация:** проверять очевидный capacity/candidate admission до физического scan; ограничить/порционировать проверку с сохранением неизменяемого подтверждённого диапазона/курсора либо выбрать жёстче меньшую территорию и измеримый единичный лимит. Делать глобальный лимит общим между соединениями; завершать validation прежде, чем сохранить colony.
- **Оценка:** **1–3 ч.-дн.** Предпосылка: оставить прямой синхронный flow, добавить раннюю capacity check и глобальный cost cap; если требуется асинхронное пользовательское строительство территории, полноценная задача/экран выйдет за этот диапазон.

### P2 — `NeedsController` полным проходом посещает жителей каждый runtime tick

- **Код:** `NeedsController.java:55-93` `tick()` начинает цикл по `registry.citizensView()` и проверяет lifecycle/admission/readiness/colony/food для каждого; вызов из `MinecraftServerRuntime.java:136-151` ставит `needs.tick(tick)` в scheduler pre-work; жительской active clock отдельный `withActiveTime` вызывается на eligible entity tick в `CitizenAdmissionService.java:303-305`; архитектурный бюджет `DIRTY_RESCAN_OBJECTS` не применяется прямо к `NeedsController`.
- **Архитектурный контракт:** §6.1 `docs/architecture.md:254-263` прямо говорит, что нет общего цикла «каждый житель анализирует всё каждый тик», а порог голода должен планировать обновление; §6.2 и §6.5 `:265-312` требуют глобальный quantum и bounded per-tick work. §14 `:613-629` повторяет событийные пороги.
- **Механизм/сценарий:** текущая проверка проходит всех граждан, включая здоровых неподходящих потребителей; eligibility ветка недорогая, но O(residents) каждый серверный тик и не расходует описанный view/scan budget. На развитии к целевым сотням citizen это устойчивый повторяющийся обход независимо от числа новых need events. `activeTimeTicks` обновляется отдельно каждый активный tick; `withActiveTime` вычисляет интервалы еды. Эти источники кода подтверждают работу, не конкретную заметность MSPT.
- **Подтверждение:** `[Статика]` полный citizen collection scan и call path; цена на целевом профиле — `[INFERENCE]`, требует централизованного profiling. `FoodNeedsTest` проверяет clocks/critical food invariants, не цену обхода.
- **Пользовательский эффект:** на большом населении needs domain отнимает повторяющуюся работу у общего сервера; при дальнейшем добавлении сна/здоровья риск превратить проход в анализ множества систем увеличится.
- **Рекомендация:** использовать пороговый event/wakeup или fair cursor с сохранённым dirty/pending; считать порционное обслуживание глобально и не терять событие между проверкой порога и парковкой. Не менять существующую семантику активного времени и приоритета еды.
- **Оценка:** **2–4 ч.-дн.** Предпосылка: достаточно ограниченного курсора/threshold queue существующего scheduler API; если нужен persistence/migration для каждого расписания — оценка увеличится.

### P2 — Частое `withActiveTime` создаёт и копирует коллекции у каждого активного жителя

- **Код:** `CitizenRecord.java:34-55` `withActiveTime` создаёт `HashMap` для needs и timer, затем новый immutable `CitizenRecord`; `CitizenAdmissionService.java:299-305` вызывает его с `activeTimeTicks + 1` на каждом активном тике.
- **Архитектурный контракт:** §6.2 `docs/architecture.md:265-281` требует измеримых ограничений времени/единиц; §6.5 и §6.6 `:305-320` разделяют state allowance/CPU и требуют измерять критическую цепочку; горячие циклы с выделениями дополнительно названы запрещаемой практикой §8.3 `:491-494`.
- **Механизм/сценарий:** даже когда `losses==0`, метод всё равно копирует `needs`/`remainingTimers` и строит новый immutable record для каждой eligible active citizen tick. Ревизия control state не повышается до потери еды, но allocation/record replacement уже случились. При 300 активных гражданах это сотни record + map construction на тик; оценка числа в секунду зависит от реального admission population/tick rate и здесь не заявляется как измерение.
- **Подтверждение:** `[Статика]` объектно-аллоцирующий горячий путь; количественный CPU/GC — `[INFERENCE]`. Родительский evidence также помечает этот путь как масштабный риск, но его runtime performance здесь не перепроверялась.
- **Пользовательский эффект:** лишний GC/копирование на сервере в критическом food/lifecycle цикле; может ухудшить время тика и способность исполнять работу, но эффект не измерен для данного call site отдельно.
- **Рекомендация:** сначала снять целевой profiler allocation profile и проверить стоимость в полном runtime; затем отделить clock update/остаток времени от immutable control DTO или уменьшить число обновлений без изменения точности/сохранения. Не скрывать паузы suppression и не менять countdown semantics ради производительности.
- **Оценка:** **2–4 ч.-дн.** Предпосылка: небольшой API change `CitizenRecord` + focused persistence/unit coverage; перенос внутреннего runtime telemetry в отдельную структуру не включает широкую migration архитектуры.

### P2 — Модель полного набора потребностей пока является только голодом

- **Код:** `CitizenRecord.java:14-18,30-37,40-55` — единственный системный ключ/таймер food, пороговый update; `NeedsController.java:16-28,55-93` создаёт только FOOD work и bread demand при `food<=6`; `FoodConsumptionExecutor.java:47-60,72-91` потребляет ровно bread и увеличивает потребность на 5; ресурсы/профессии содержат хлеб не как процесс производства, а как единичный stock item; `NeedsGameTests.java:25-38` имеет food-specific сценарии.
- **Архитектурный контракт:** §2 `docs/architecture.md:59-86` перечисляет food, sleep, happiness, health, security; §14 `:613-641` связывает питание/отдых/здоровье/безопасность с допуском исполнителя, расписанием, порогами и отдельными системами. §22 не требует полного набора этого контента на раннем этапе.
- **Механизм/сценарий:** food реализован end-to-end: active clock и residual, голодный потребитель, critical work/demand, доставка со склада, проверка канонического citizen inventory, native bread expense и recovery evidence. Сон/усталость, счастье, здоровье/болезни и безопасность/угрозы в рассмотренном `CitizenRecord`/`NeedsController` пути и content definitions не реализованы. Это **отсутствие предметного контента**, не нарушение food инварианта.
- **Подтверждение:** `[Статика]` модель и call sites содержат только `food`; `ContentLoader.java:64-65,135-137` задаёт текущие виды shipped definitions, а process JSON — лишь `oak_planks` и `oak_stairs`. Отсутствие других content families в репозитории не означает, что ранний технический этап обещал их уже иметь.
- **Пользовательский эффект:** игрок получает базовую поддержку голода, но не полный жизненный цикл потребностей/поведения из продуктовой карты; нельзя считать поле `needs` в DTO реализацией нужд, отличных от еды.
- **Рекомендация:** согласовать staged MVP requirements отдельно (минимум определённые правила food + sleep/rest?); для каждой следующей нужды задать хранение/активное время/пороговую инвалидацию/влияние на assignment/работу и физический исполнитель до добавления массива произвольных counters. Не выдавать все §2 как уже присутствующую функцию.
- **Оценка:** **15–30 ч.-дн.** для простых, first-pass rest/sleep, health/safety, happiness verticals вместе (примерно 3–8 дня на домен), при наличии утверждённых предметных правил и повторном использовании текущих scheduler/storage patterns. Не включает боевую систему, медицину, животноводство, угрозы/рейды, deep balancing или UI-карту.

### P2 — Management UI/protocol пока даёт 4 плоских списка, не все поверхности §19.2

- **Код:** `ManagementProtocol.java:17-18,83-93` — только SUMMARY/CITIZENS/BUILDINGS/WORK и семь bounded row-полей; `ManagementViews.java:117-226` строит данные этих категорий; `ColonyScreen.java:151-195` рисует четыре вкладки и строки; `ManagementBackend.java:78-103` использует тот же preparation pipeline.
- **Архитектурный контракт:** §19.2 `docs/architecture.md:799-814` проектирует ratушную сводку, отдельное конкретное здание, отдельного жителя, очередь и карту с ограниченной областью/детализацией; §19.3 требует client-only separation.
- **Механизм/сценарий:** текущие страницы включают aggregate member/stock/limits, списки жителей, регистрации/мастерские, generic work; отдельного ID-scoped citizen/workshop detail projection, map/range view или queue-specific sorting/filter surface в протоколе нет. Это **недостающие UI-продуктовые поверхности**, не утечка или нарушение текущего authorization: каждый имеющийся view снова scope-check-ится.
- **Подтверждение:** `[Статика]`; не утверждается, что MVP обязательно требует карты или каждого §19.2 surface. Нужные initial MVP screens должны быть определены владельцем продукта.
- **Пользовательский эффект:** мало объяснимой детализации при отладке отдельного жителя/здания/цепочки работы; карта и specialized queues недоступны, даже если underlying domain расширится.
- **Рекомендация:** определить минимальный MVP views-first, например summary + selected citizen + selected work/order; дополнить bounded typed projections и selection IDs с повторной проверкой scope/revision, а не передавать full registry. Карта/геопространственная детализация может остаться за первым MVP, если это явно утверждено.
- **Оценка:** **8–15 ч.-дн.** для selected citizen/building/work details и маленького игрового потока на имеющемся protocol/page machinery; assumptions — карта не входит, новые game systems вне оценки.

### P2 — Экран оперирует raw resource IDs и требует вручную вводить UUID игрока

- **Код:** `ColonyScreen.java:160-174` отображает технические ID/row detail, `:285-292` переключает choice вариантом `Component.literal(value)`, `:350-360` принимает UUID строкой для member/owner; формы creation/storage/workshop вводят координаты текстом `:228-280`; `ManagementText.java:1-38` локализует названия/коды, но raw choice value отображается буквально; `en_us.json:19-52` и `ru_ru.json:19-52` содержат подписи действия/полей.
- **Архитектурный контракт:** §19.2–19.3 `docs/architecture.md:799-818` требует удобных bounded представлений, адресной синхронизации и изоляции клиента; §2 включает интерфейс управления колонией/жителями.
- **Механизм/сценарий:** форма не предлагает nickname/profile lookup для передачи членства и выбора владельца, поэтому игроку нужен UUID, при этом проверка повторения UUID есть только для transfer ownership. Profession/blueprint choices представлены namespaced ID, а не display labels. Текущая локализация покрывает подписи и известные состояния, но не превращает произвольные content IDs в человекочитаемые названия.
- **Подтверждение:** `[Статика]`; это usability/usability-a11y gap, не protocol authorization issue. Сервер проверяет права независимо от UI.
- **Пользовательский эффект:** ручной ввод UUID ошибкоопасен и неудобен для приглашения; техничные IDs делают screen плохо объяснимым для обычного игрока, хотя базовая форма и двуязычные подписи существуют.
- **Рекомендация:** добавить ограниченный онлайн/profile display-name resolution с явным подтверждением неизменяемого UUID; определениям контента дать display-name translation key и fallback на ID. Сохранить UUID как authoritative target, не полагаться на клиентскую метку/имя для authorization.
- **Оценка:** **2–4 ч.-дн.** Предпосылка: онлайн-поиск в текущем мире и display names у существующего shipped content, без нового внешнего profile service/бродкастов online player directory.

## Подтверждённые реализации / положительные evidence

1. **Границы полномочий.** ManagementSession даёт предварительное `authorize` по членству (`ManagementBackend.java:33-36`); тело команды дополнительно ограничивает объект той же колонией (`:37-47`), core повторно применяет ранги к `assign`, `setMember`/`setOwner` (`ColonyCommands.java:78-93,115-124,296-306`). Manager не получает OWNER-only member/ownership изменение: отказ из core превращается в `ACCESS_DENIED` (`ManagementSession.java:128-145`). UI `allowed` только presentation; не authority (`ColonyScreen.java:112-117`). Авторизационного обхода management-команд в просмотренном пути статически не обнаружено.
2. **Жизненный цикл игрока/колонии.** `colonyloom ui` открывает создание (null colony); `ui <UUID>` допускает участника, в т.ч. viewer, к открытию экрана: `ColonyloomBrigadier.java:23-30`, `ManagementNetwork.java:87-104`. `CreateColony` проходит session command gate, core проверку игрока, overlap/territory, registry admission и затем auto-opens колонию после ACCEPTED: `ColonyScreen.java:365-386`, `ManagementClient.java:98-131`. `setMember`/`setOwner` меняют `authorityRevision`, что отзывает кэшированные страницы/результаты. Это существующий вход/передача владения; он не заменяет найм из P1.
3. **Bounded management wire.** Protocol фиксирует 8 KiB command, 32 KiB view, 256-byte UTF-8 strings, 50 row/page, 64 catalog entries, 128 cached results/64 KiB, 4 subscriptions/256 KiB view buffer, 20 commands/20 ticks, send interval 10 ticks, ACK timeout 100 ticks: `ManagementProtocol.java:11-14,83-93`; codecs отвергают over-limit и trailing bytes `ManagementPayloads.java:21-36,50-99,135-154`; client command sequence не повторяется через reconnect `ManagementClient.java:20-29,82-114`.
4. **Снапшоты, ACK, revoke.** Сессия обновляет authority, сверяет страницу до/после подготовки и перед отправкой; revision change чистит stale pending/in-flight данные; ACK timeout закрывает view: `ManagementSession.java:185-216,225-285`. На send уходят snapshot/delta с `authorityRevision`/`stateRevision`, клиент проверяет base revision и resync-ится: `ManagementSession.java:308-355`, `ManagementClient.java:130-181`. Это соответствует §19.2 revoke semantics: уже отправленное знание отозвать нельзя, но следующая выдача переавторизуется.
5. **Порционное представление.** `ManagementViews.Preparation.advance` списывает `VIEW_ROWS` service budget на каждой посещённой строке и перепроверяет actor/authority; строки ограничены одной сетью/страницей (`ManagementViews.java:86-114,117-226`; `ManagementSession.java:306-330`). Foreign rows также считаются единицей и не попадают в результирующее view.
6. **Dedicated client separation.** Client-only мод объявлен `Dist.CLIENT` и связывает управление/экран только там: `ColonyloomClientMod.java:8-36`; общий сетевой registrar работает с generic payloads и публикует common carrier event, не загружая `Screen` на сервер (`ManagementNetwork.java:32-59`, `ManagementClientPayloadEvent.java:1-20`). По исходнику граница §19.3 соблюдена.
7. **ActionContext/current principal.** `ActionContext.java:7-16` содержит colony, citizen, action kind, target, authority mode, initiator/revision. Physical construction/transfer/craft/food создают COLONY-mode контекст с текущей authority revision (`MinecraftConstructionService.java:136-140`, `MinecraftConstructionSupply.java:166-168`, `MinecraftDeliveryService.java:282-285`, `MinecraftProductionService.java:105-108`, `FoodConsumptionExecutor.java:47-60`); соответствующие executors перед native mutation перепроверяют state/principal/assignment. NeoForge integration публикует cancellable native action events: `ColonyloomMod.java:82-84`, `NeoForgeRecipeProtection.java:12-18`. Это не generic claims-mod integration и не доказательство совместимости со всеми protection mods; эта граница отдельно рассмотрена родительским slice.
8. **Food vertical slice.** Citizen хранит только food level 0..20 и exact residual interval 1200 active ticks; при голоде ≤6 gameplay создаёт critical food work и bread demand; `MinecraftNeedsService` использует общий delivery service; исполнитель проверяет current canonical citizen inventory/epoch, exact allocation, claim guard, before+after, native bread item and protection, а ambiguous side effect блокирует recovery без автоматического replay: `CitizenRecord.java:14-55`, `NeedsController.java:55-93,111-129`, `MinecraftNeedsService.java:23-55`, `FoodConsumptionExecutor.java:41-120`. Это подтверждает реализованное питание, не более широкую needs suite.
9. **Content/localization.** `ContentLoader.java:49-65,104-138` ограничивает число definitions/размер и проверяет required `builder`, `courier`, `carpenter`, `stair_strip`, `oak_planks`, `oak_stairs`. В ресурсах видны три профессии (`colonyloom/professions/{builder,carpenter,courier}.json`), два процесса (`processes/{oak_planks,oak_stairs}.json`) и один обычный blueprint (`blueprints/stair_strip.json`). `en_us.json`/`ru_ru.json` имеют подписи экранов/форм и state/reason keys (`:1-152`); для просмотренных соответствующих блоков набор keys парный. ### Связь с §21.2 / §22

- **§21.2 fulfilled/covered на уровне исходников:** неполномочный клиент; bounded decode; slow client/result buffer; bounded paging/progress/foreign scope; food subject/allocation/physical bread; persistence residual/no duplicate consumption. Сценарии намеренно проверки contracts, не только unit mocks.
- **§21.2 открыто для этого slice:** packet/subscription flood, глобальный суммарный rate нескольких сессий на preparation/error response, member-state cap, измерение territory preflight и needs per-tick cost на целевой population. Не утверждается, что защита уже обходится; отсутствует проверка/limit на соответствующих входах.
- **§22 подтверждено структурно:** server authority/core commands, persistence-ready food state, bounded network and client separation. §22 заключает «завершено поведение»; по отсутствию обычного citizen intake ещё нет самостоятельного playable settlement bootstrapping без оператора. Ближайший приоритет — закрыть P1 recruitment/player flow, выбрать ожидаемую needs subset, затем повторить реальный client/server acceptance.
- **Не превращать отсутствие контента в invariant breach:** всё перечисление §2 и домены §14 — широкий функциональный охват. Три профессии, два рецепта, один blueprint и food-only need — узкий набор фактического контента. Дефицит не уничтожает уже существующую пищевую бухгалтерию или права протокола.
