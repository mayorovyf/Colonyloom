## Замечания

### P1 — Отсутствующий DTO безусловно трактуется как новый мир; dirty marker не проверяется

- **Код:** `colonyloom-minecraft/src/main/java/io/github/kpuctajluk/colonyloom/minecraft/persistence/ColonyPersistence.java:47-53`, `open`; dirty-marker write — `:103-117`; marker validation — `:192-199`.
- **Архитектурный контракт:** §17.2 `docs/architecture.md:717-733` — corrupt/lost state не должен молча превращаться в пустую колонию, recovery не должен считать неизвестность пустым состоянием; §17.4 `:743-755` — независимые durability sides требуют явной политики.
- **Механизм:** код выбирает `ColonySavedData.empty(...)`, когда `colonyloom.dat` отсутствует (47–50), а затем вычисляет `clean = !existing || previousMarkerClean(...)` (53). Поэтому при отсутствующем DTO marker никогда не читается. Первая долговременная мутация записывает `clean=false` до следующего autosave; авария/потеря файла DTO между marker и DTO save при следующем старте становится пустым реестром с `clean=true`.
- **Доказательство:** `[подтверждено статически]`; сценарии source покрывают dirty marker плюс сохранённый DTO и штатный clean checkpoint, но не dirty marker + отсутствующий DTO (`DeathRecoveryScenario.java:174-204`, `ConstructionScenario.java:117-134,172-176`).
- **Пользовательский эффект:** логическая потеря колоний, identity, обязательств и witnesses; оставшиеся physical entities/inventories мира могут стать orphaned и не появится recovery quarantine. Это не просто отсутствие данных: несогласованность уже сигнализировалась persisted dirty marker.
- **Рекомендация:** при отсутствии DTO отдельно читать marker: отсутствие обоих допускает первый запуск; присутствующий/повреждённый marker должен fail closed и требовать явного recovery/reset. Добавить dedicated crash/restart сценарии: first mutation, dirty marker durable, DTO отсутствует/нечитаем, marker не переписывается и мир не активируется пустым.
- **Оценка:** 1–2 человеко-дня при текущем marker v1 и имеющихся IO helpers, включая fixture и тест; предпосылка — сохранить различие virgin world / состояние, где уже существовал Colonyloom session.

### P1 — Сущность смерти переводится в DEAD до окончательного исхода cancellable LivingDeathEvent

- **Код:** подписка `ColonyloomMod.java:51-55` (`EventPriority.LOWEST`, receiveCanceled=false), dispatch `:192-195`; обработчик `IdentityPlatform.java:95-124`; lifecycle commit `ColonyCommands.java:230-266`; native effect только после смерти — `CitizenEntity.java:194-220`.
- **Архитектурный контракт:** §14 `docs/architecture.md:627-630` — смерть меняет lifecycle, но не выгрузка; §17.4 `:743-755` — witness и неопределённость должны соответствовать подтверждённой физической стороне.
- **Механизм:** в вызове listener для ещё не-canceled события handler сначала готовит PREPARED evidence, делает `markDeath` (DEAD+tombstone, снимает work assignment), quarantine и capture, а drop path вызывается после возврата из death-event dispatch. Другой listener с более поздним порядком может отменить то же событие; в таком случае native death/drop не выполняется, а death observer здесь не откатывает lifecycle/effect и не вызывает `markRecoveryBlocked`.
- **Доказательство:** commit-before-event-dispatch-return подтверждён статически. Поздняя отмена другим listener и конкретный vanilla/loader результат — `[INFERENCE]`; кода, финализирующего cancellation, и теста cancellation-after-Colonyloom не обнаружено.
- **Пользовательский эффект:** физически живой entity с cargo остаётся логически DEAD, не участвует в работе и недоступен для обычного инвентарного взаимодействия. PREPARED witness может сохраниться при clean shutdown без явного recoveryBlocked; если entity позднее умирает, первый hook для canonical ALIVE entity уже не ведёт смерть как исходную операцию.
- **Рекомендация:** переносить логическую фиксацию на точку после подтверждённой смерти либо после dispatch проверять cancellation и переводить результат в явное recovery-blocked/reconciliation-состояние; добавить loader test с listener, отменяющим событие после Colonyloom observer. Не превращать это в автоматическое повторное выполнение drop.
- **Оценка:** 2–4 человеко-дня, если в 1.21.1/NeoForge доступен надёжный post-dispatch hook с нужной семантикой; 4–7 дней при необходимости вводить отдельный двухфазный death state и мигрировать DTO/effect lifecycle.

### P1 — Death recovery inspect не наблюдает ItemEntity destination и принимает несверяемую смерть

- **Код:** death witness содержит `inventoryHash` и count-only — `IdentityPlatform.java:99-121`; inspection `effectSnapshot` направляет любой effect без transfer/craft на `observedBlock(effect.target())` (`IdentityPlatform.java:367-375`); `inventorySnapshot` сериализует loaded citizen inventories и storage containers, но не world ItemEntity (`:339-357`); accept повторно сравнивает только inventory/site/effect/storage/supply snapshots (`:316-338`). Сценарий смерти требует лишь наличия строки `actualPhysical=` — `DeathRecoveryScenario.java:260-261`.
- **Архитектурный контракт:** §14 `docs/architecture.md:627-630`; §§17.2–17.4 `:717-755` — сверка entities/inventories и заранее выбранные стороны/witness для смерти; §21.2 `:871-899+` — interruptions для смерти должны следовать выбранной политике.
- **Механизм:** для `Kind.DEATH` нет transfer/craft, поэтому public inspect фактически показывает блок по координате смерти, не список/UUID/type/count emitted ItemEntity. `inventorySnapshot` может обнаружить изменение загруженного source entity, но не сравнивает drops; без сохранённых IDs/слотового состава witness не связывает native drop entities с исходным inventory. Между inspect и accept предмет может переместиться/исчезнуть, и проверка останется прежней, если source inventory неизменен.
- **Доказательство:** отсутствие ItemEntity-сверки и fallback на block подтверждены статически. Потеря после инспекции вследствие удаления/подбора drop — `[INFERENCE]`; сам сценарий сохраняет те же drops и тестирует отсутствие replay, не внешний сбор/изменение drop.
- **Пользовательский эффект:** operator может принять recovery, не видя фактической судьбы гражданского cargo; crash после source removal либо внешний veto/изменение drop может принять потерю без информированного предметного решения. Наблюдаемая строка физического состояния не соответствует типу эффекта.
- **Рекомендация:** добавить death-specific durable evidence состава source inventory и наблюдаемых published drop UUID/type/count, а recovery inspect выводить source/cargo/drop/unknown отдельными значениями. При невозможности сопоставить drop destination выводить UNKNOWN и требовать явного отдельного решения; добавить test, меняющий/удаляющий drop между restart и inspect/accept.
- **Оценка:** 3–5 человеко-дней при доступном окончательном drop event и устойчивом идентификаторе emitted drops; 5–8 дней при необходимости менять schema и поддерживать неоднозначные/собранные до рестарта предметы. Оценка предполагает без общего transaction/rollback.

### P2 — Opaque unknown NBT сохраняется и блокируется, но причина/перечень недоступны оператору

- **Код:** unknown type/schema переходит в retained NBT и `blocked` — `RegistryNbt.java:38-88`, dependency handling `:120-180` и `:294-296`; retained count API — `ColonySavedData.java:84-86`, adapter getter `ColonyPersistence.java:97-101`; публичная сводка показывает только общий `RECOVERY_AMBIGUOUS`/`CONTENT_UNAVAILABLE` — `ManagementViews.java:132-134`; `/recovery inspect` выводит известные citizens/effects/sites, не retained record type/schema — `IdentityPlatform.java:300-312`.
- **Архитектурный контракт:** §16.2 `docs/architecture.md:691-701`: неизвестный тип сохраняется, затронутый объект блокируется **с диагностикой**, зависимые work получают явную недоступность; §§17.2–17.3 требуют видимого Blocked state.
- **Механизм:** целостность оригинального CompoundTag обеспечена, зависимость изолируется; однако число opaque записей даже не потребляется вне getter. В статусе нет списка неизвестных `typeId`, schema, object UUID/dependencies, поэтому нельзя понять причину, scoped version или путь исправления без анализа файла.
- **Доказательство:** подтверждено статически (поиск consumer `retainedRecordCount()` нашёл только declaration/getter; management status общий). Unknown-codec tests проверяют retention/blocking, но не operator-facing cause (`PersistenceGameTests.java:173-215`, `ConstructionPersistenceGameTests.java:74-95`, `SupplyPersistenceGameTests.java:88-105`).
- **Пользовательский эффект:** безопасный fail closed вместо порчи, но неоперабельное восстановление/эскалация к ручному NBT, риск бессрочно отключённой целой colony из-за неизвестного элемента.
- **Рекомендация:** ограниченная scoped recovery report (`typeId`, schema, stable IDs, dependency edge, opaque count/size, why blocked) в inspect/status; не декодировать неизвестный payload и не раскрывать NBT клиенту. Проверить ограничение размера вывода.
- **Оценка:** 2–3 человеко-дня на серверный read-only diagnostic + test; 3–4, если нужен versioned/постраничный UI/network projection. Предпосылка — diagnostics не меняют состояние и доступны operator-only.

### P2 — Root-format migrations пока не существуют, кроме одной production-order v1→v2

- **Код:** root codec строго принимает schema 1 и отвергает любую другую (`RegistryNbt.java:38-43`); текущий migration backup/conversion реализован только для `production_order` schema 1 в `ColonySavedData.java:42-62`, парсер/convert — `SupplyNbt.java:91-116` и `:142-160`.
- **Архитектурный контракт:** §16.1 `docs/architecture.md:680-689` — schema состояния и migration при изменении формата; §17.1–17.2 `:703-733` — долговременные записи версионируются, загрузка включает migration, исходник резервируется до деструктивного преобразования.
- **Механизм:** всякий root schema >1 делает весь `preflight` unavailable; сохранение не перезаписывает source (это безопасно), но перенос уже созданного мира на новую версию невозможен. Единственный migration путь узкоспециализирован; будущие поля/перекладки citizen/binding/marker не имеют compatibility step.
- **Доказательство:** подтверждено статически. Это **не текущая потеря данных** и не повод считать сохранение corrupt: future schema fail closed и original не заменяется (`PersistenceGameTests.java:115-144`). Если schema 1 ещё не опубликована игрокам, это незакрытый MVP/upgrade capability, а не regression.
- **Пользовательский эффект:** обновление формата позже потребует остановить старую версию, ручной инструмент/backup/restore или откажет в запуске; downgrade также явно не поддерживается.
- **Рекомендация:** до выпуска меняющего формат релиза указать переходную migration path и immutable compressed backup; не добавлять «generic migration framework» до конкретного формата, но включать тесты для каждого нового version boundary. Отдельно не считать одно production migration обещанием общей схемы миграций.
- **Оценка:** сейчас 0.5–1 день на формализованную release/backup policy; на каждую реальную root DTO migration 2–5 дней с fixture/backup/rollback тестами. Предпосылка: migration определяется следующей schema, поэтому полный converter не оценивается без её полей.

### P2 — Объём binding history конечен и overflow превращается в глобальное identity failure

- **Код:** `BindingRegistry.MAX_OBSERVATIONS=600`, throw при добавлении UUID — `BindingRegistry.java:12-19,37-45`; rebind помечает все невыбранные embodiments retired, но не удаляет их — `:79-99`; restore сохраняет observations (`:120-135`); `IdentityPlatform.join/leave` на любом RuntimeException фиксируют глобальный `identityFailure` и карантинят все loaded NPC — `IdentityPlatform.java:49-78`; `requireAvailable` затем блокирует команды (`:402-407`).
- **Архитектурный контракт:** §5.2 `docs/architecture.md:206-226`: поздние старые/duplicate embodiments не удаляются и не получают доступ, новая эпоха связывается явно; §17.4 `:743-755` требует безопасной политики очистки маркеров/свидетельств. Сама boundedness обязательна, бессрочное хранение identities также осмысленно.
- **Механизм:** максимум 600 lifetime observation UUID, при 300 residents оставшаяся ёмкость нужна конкурентным/retired entities. `applyBind` не имеет compaction; последовательные пересоздания UUID/реальные unresolved duplicates потребляют history. Когда новый loaded entity встречает cap, `IdentityPlatform.join` превращает локальный overflow в `identityFailure`, который отключает identity-dependent commands для всего сервера. Это bounded отказ, не unbounded memory growth.
- **Доказательство:** граница и catch/global latch подтверждены статически; конкретная частота игрока, приводящая к 600, — `[INFERENCE]`. 300-resident compressed reload покрыт source test `PersistenceGameTests.java:33-58`, duplicate/rebind — `ColonyCommandsTest.java:75-110,160-184`; cap overflow и восстановление после него не покрыты.
- **Пользовательский эффект:** при достаточном числе исторических duplicate/rebind identity reconciliation остаётся заблокирована до следующего restart/recovery path; из-за глобального latch даже незатронутые citizens перестают обслуживаться. Простая чистка retired UUID небезопасна, если старое entity может позже загрузиться.
- **Рекомендация:** документировать lifetime cap и операторский способ восстановления/понижения истории; test на cap/overflow и убедиться, что ошибка не может смешаться с partial join. Любую компактацию проектировать с durable retired-generation/tombstone semantics, а не безусловным удалением наблюдений.
- **Оценка:** 1–2 чел.-дня для явно диагностируемого scoped refusal и overflow GameTest; 3–6 дней для расширения durable retirement representation и безопасного удаления/recovery semantics. Предпосылка: нельзя удалять историю до доказуемо безопасной границы поздней загрузки.

## Подтверждённые реализации

1. **Durable persistence gate и checkpoint:** `ColonyPersistence.java:35-81,103-230` открывает exact bounded preflight и attaches exact SavedData; `ensureSessionDirty` пишет marker до mutation; `capture` обновляет SavedData snapshot; shutdown stop выполняется перед clean (`MinecraftServerRuntime.java:236-258`); `checkpointAndClean` сохраняет world, ждёт IO, сравнивает forced DTO с ожидаемым envelope и только после этого ставит clean (`ColonyPersistence.java:155-188`). На compaction checkpoint marker остаётся dirty (`:137-153`).[подтверждено статически]
2. **Bounded NBT IO:** `DurableNbt.java:14-60` ограничивает DTO 96 MiB/marker 64 KiB, проверяет compressed read через `NbtAccounter`, пишет temp, force, roundtrip, atomic rename и final verify. Явно нет атомарности между SavedData и chunks/entities (`:14`). Ошибка IO устанавливает persistence unavailable, не пустой runtime (`ColonyPersistence.java:68-81`).[подтверждено статически]
3. **Explicit versioned DTO и restore:** root codec явный, schema 1; `RegistryNbt.java:28-90,124-296,295-654` декодирует записи по типу, проверяет их limits/references/dependencies, сохраняет unknown tags копией. `ColonyRegistry.restore` валидирует whole registry и admission limits, подготавливает aggregate restore до замены canonical maps (`ColonyRegistry.java:135-227,269-340`). Readiness восстановленного entity не доверяется сохранённому READY (`:164-166`), а все bindings становятся unloaded (`BindingRegistry.java:120-135`). Tests проверяют roundtrip/unknown/corrupt/schema bounds и restore-without-mutation (`PersistenceGameTests.java:33-58,115-215,219-280`; `ConstructionPersistenceGameTests.java:64-120`).[подтверждено статически]
4. **Recovery quarantine:** при сохранённом DTO dirty/mismatch marker вызывает `markRecoveryBlocked` и forced `writeSnapshot` до server attachment (`ColonyPersistence.java:52-67`); recovery accept требует operator, совпадающий checkpoint, fresh loaded/ready citizens, revisions, work/claims/effects/sites, platform checks и recheck, после чего cancellation/release обязательств и lifecycle reconciliation совершаются без компенсации предметов (`ColonyCommands.java:174-203`). Minecraft-level accept дополнительно сравнивает inventories/sites/effects/supply/storage до core commit (`IdentityPlatform.java:313-338`).[подтверждено статически]
5. **Unknown content — сохранность и изоляция:** unknown/mismatched `typeId`/nested schema сохраняется как исходный NBT; неизвестные зависимости work/citizen/storage/supply/evidence распространяют block на затронутые колонии (`RegistryNbt.java:68-88,94-116,144-215,294-296`; `SupplyNbt.java:19-67`; `ConstructionNbt.java:92-141`). Отсутствующие ссылки отдельно reject-ятся, не маскируются opaque sibling. Root unknown version отказывает в load целиком и не заменяет исходник. Это intentional fail closed, не доказательство silent data loss.
6. **Binding/physical entity:** core registry — авторитет; `BindingRegistry` сравнивает citizenId/entity UUID/binding epoch, quarantines stale/duplicate/unrecorded embodiments и не владеет inventory (`BindingRegistry.java:10-118`). `CitizenEntity` сохраняет native 9-slot inventory в entity NBT и при load принудительно quarantine (`CitizenEntity.java:155-190`, частично не раскрыто в этой проверке); новое воплощение создаётся только command path (`IdentityPlatform.java:167-185`). Ordinary unload обновляет observation и не создаёт entity (`IdentityPlatform.java:64-78`).
7. **Death:** `ColonyloomMod` пропускает отменённые на момент listener события и обрабатывает только canonical alive UUID/epoch (`ColonyloomMod.java:51-55,192-195`; `IdentityPlatform.java:95-103`). До physical source effect ставит dirty marker и PREPARED witness; затем `markDeath` ставит DEAD+tombstone/quarantine и capture; `dropEquipment` удаляет actual inventory stacks и передаёт vanilla `spawnAtLocation`; после `super.die()` observer смотрит remaining source (`CitizenEntity.java:194-220`; `IdentityPlatform.java:99-124`).[подтверждено статически]
8. **Effect/compaction:** `EffectRegistry.prepare/update` резервирует evidence до физического шага, разрешает PREPARED→OBSERVED/AMBIGUOUS и запрещает изменение identity/attempt; only OBSERVED/ACCEPTED compaction, при отсутствии blocked colonies (`EffectRegistry.java:23-63,64-82`). `MinecraftServerRuntime` вызывает durable checkpoint до compaction и persistence snapshot после (`MinecraftServerRuntime.java:196-225`). Unresolved PREPARED/AMBIGUOUS сохраняются.[подтверждено статически]

## Смерть: crash sides и duplication/loss

- До native эффекта `IdentityPlatform.death` записывает PREPARED `EffectRecord`, countBefore и hash всего source inventory, затем canonical DEAD+tombstone; source side пока прежняя (`IdentityPlatform.java:99-124`).
- После каждого slot removal `CitizenEntity.dropEquipment` вызывает `AFTER_SOURCE_CHANGE`; между `removeItemNoUpdate` и `spawnAtLocation` есть короткое окно source-empty/destination-absent (`CitizenEntity.java:198-207`).
- После возврата `super.die` fault point сигналит after destination; только затем `remaining` observer переводит witness в OBSERVED/AMBIGUOUS и capture (`CitizenEntity.java:212-220`; `IdentityPlatform.java:108-118`).
- Отдельный after-fact/before-notify point выполняется после обновления witness, до capture (`IdentityPlatform.java:110-113`).
- Dedicated scenario source фиксирует исходное значение `stairs=4,bread=3`, пишет independent native entity state и ожидаемые raw MCA/entity UUID counts. `death_after_source_change` специально ожидает source=0, drops=0, PREPARED: существующий инвентарь теряется, повторное создание/компенсация запрещены; destination/fact points сохраняют исходные drops и UUID. `DeathRecoveryScenario.java:140-204,227-258,279-329`.
- Эти assertions показывают **заданную current policy**: антидублирование имеет приоритет над отсутствием потерь; после ambiguous recovery admin может accept exact current physical world без item creation/removal. Это не exactly-once и не без потерь, что архитектура §17.4 допускает только при заранее описанной policy. ## §22: завершённость именно этого slice

- **В значительной степени реализовано:** identity/lifecycle/rebind gates; bounded DTO; clean checkpoint; known schema validation; unknown records retain/block; real native inventory; operator recovery acceptance; compaction for terminal witnesses. §22 lifecycle stage — source tests предусмотрены (`PersistenceGameTests`, `IdentityScenarioMod`, `DeathGameTests`).
- **Не завершено для MVP по подтверждённому runtime:** маркерная ветвь missing DTO, death cancellation finality, death item destination reconciliation/diagnostics. §22 требует заранее выбранную политику физического эффекта и restart/interruption proof; в сценарии source-only loss policy явно есть, но final event/destination integrity — нет.
- **Неизвестно:** загрузчик/другие mods дают фактический приоритет/изменение `LivingDropsEvent` здесь не испытывалось; GameTests и crash matrix не выполнялись. Нельзя объявлять test source зелёным результатом.
- **Не относится к текущему slice:** отсутствие исследований, quests/reward, медицина/revive, расширенного поведения жителей — это отсутствие контентных систем (§14), не повреждённая запись/нарушение persistence invariant. Не оценивалось как defect.
