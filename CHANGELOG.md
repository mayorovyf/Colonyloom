### Stage 02 — ownership, physical identity and persistence

- Persistent colony UUIDs, nonoverlapping dimension-scoped territories, OWNER/MANAGER/VIEWER rights, citizen UUID/entity UUID/binding epoch, lifecycle, needs and remaining active-time timers. Only the explicit operator command creates a physical citizen; unload never creates a replacement.
- Persistent humanoid citizens have actual nine-slot Minecraft inventories and vanilla ground navigation without wandering goals. Authorized owners/managers open the existing inventory through a vanilla menu; every click rechecks current rights and binding. Duplicate, stale and unrecorded embodiments retain their items in quarantine.
- Commands: `colony create <name> <from> <to>`, `member set <colony UUID> <player> <manager|viewer|none>`, `owner set <colony UUID> <player>`, `citizen create <colony UUID> <pos>`, `citizen assign <citizen UUID> <namespaced profession>`, and `status <colony UUID>`, all below `/colonyloom`. Player arguments resolve standard Minecraft profiles; professions builder/courier/carpenter are loaded and validated as one bounded definition set, not executed jobs yet.
- Explicit schema-1 SavedData DTOs use bounded preflight reads before attachment. Corrupt/newer schemas disable mutations without replacing the file. Unknown records retain their original NBT; identifiable dependent colonies are blocked, unrelated colonies are not. Known IDs are checked even when their records are retained because a dependency is unknown.
- A verified dirty session marker precedes mutation. Normal shutdown flushes Minecraft, forces/rereads the exact DTO, then writes a matching clean checkpoint. A dirty/undefined previous marker persistently blocks affected colonies; later clean shutdown alone does not clear that block.
- Operator-only `recovery inspect`, `recovery bind` and `recovery accept-world` expose/revalidate identities and actual items. Bind requires every known competing embodiment loaded and advances the chosen epoch without deleting competitor property. Accept rejects wrong checkpoints, unloaded/stale observations and changed physical inventory; successful acceptance creates/removes no items.
- Exercised dedicated scenario: two colonies, three physical citizens, roles/professions and exact inventories; stale duplicate quarantine, unloaded competitor refusal, epoch-advancing bind, then clean restart with the same UUIDs/epochs/property. Dirty-marker fixture remained blocked through a subsequent clean stop/restart; incomplete/stale/changed-inventory acceptance was refused before final property-preserving acceptance.
- Exercised actual graphical client: humanoid rendering and nine-slot inventory; integrated-world provisioning and a separate integrated world with both prior colony IDs unknown, all three prior entity UUIDs absent and zero citizen entities. Actual corrupt-save startup, command refusal and clean shutdown retained all 86 fixture bytes. This stage does not establish scheduled work, economy execution or NPC scale.
- Local evidence: `runs/server/colonyloom-identity-02b/colonyloom-identity-observations.jsonl`, integrated worlds' matching observation logs, and `build/client-stage02-citizens.png`, `client-stage02-menu-inventory.png`, `client-stage02-integrated-setup.png`, `client-stage02-isolation.png`, under `colonyloom-neoforge`. Disposable worlds/evidence are excluded from the JAR.

Run from repository root with JDK 21: `./gradlew build` (PowerShell: `.\gradlew.bat build`). Minecraft dev tasks belong to `:colonyloom-neoforge`; run the physical regressions with `:colonyloom-neoforge:runGameTestServer`. Dedicated instances require the environment owner's accepted Minecraft EULA; builds do not accept it automatically. `runServer` forwards console input so `stop` performs normal shutdown. Development-only `/colonyloomtest identity setup|verify|conflict|recovery-check|isolation` scenarios require a real connected operator and an explicitly marked disposable world; they are excluded from release.
